# Reminders Specs

LLD: `docs/llds/reminders.md`

---

## Data Model

- [x] **REM-DATA-001**: The system shall hold at most one `Reminder` per category, keyed by `categoryId`, and deleting a category shall delete its reminder with it. How that deletion is enforced in storage is `docs/specs/local-storage.md`'s (LS-BE-072); cancelling the category's live `AlarmManager` alarm is separate and is the deleting caller's job (REM-SCHED-012, invoked from the delete flow per `docs/specs/category-management.md`, CAT-UI-007).
- [x] **REM-DATA-002**: A `Reminder` row shall store `enabled`, `mode` (`FIXED` or `RANDOM`), `times` (FIXED-mode clock times), `windowStart`/`windowEnd`/`occurrencesPerDay` (RANDOM-mode window config), `daysActive`, `showCategoryInNotification`, and `nextFireAt` together in one flat schema; switching `mode` shall not clear or overwrite the fields belonging to the other mode, so a user's prior configuration for a mode is preserved when they switch back to it.
- [x] **REM-DATA-003**: The Category Edit screen's reminder UI state shall default `showCategoryInNotification` to `false` for a category with no existing reminder.
- [x] **REM-DATA-004**: The Category Edit screen's reminder UI state shall default `daysActive` to all seven days for a category with no existing reminder.
- [x] **REM-DATA-005**: `nextFireAt` shall store the instant this device last armed (or attempted to arm) for the reminder's currently-pending alarm; it shall be null whenever the reminder is disabled or has not yet been armed. It is this device's own record of what it told `AlarmManager`, not a value recomputable from the reminder's configuration alone.
- [x] **REM-DATA-006**: `saveCategory(category, reminder)` shall persist the category's fields and its `Reminder` config atomically — either both land or neither does, with no state in which a category's saved fields disagree with its saved reminder. Passing no reminder shall leave whatever is stored untouched rather than clearing it, which is what every caller that does not edit reminders needs; a reminder is switched off by storing it with `enabled = false` (REM-DATA-005), and only deleting the category removes its row (`docs/specs/local-storage.md`, LS-BE-072). The storage mechanism is `docs/specs/local-storage.md`'s (LS-BE-015).
- [x] **REM-DATA-007**: `getAllEnabledRemindersOnce()` shall return every `Reminder` row with `enabled = true` as a one-shot (non-`Flow`) list, for use by boot/clock-change re-arm and startup reconciliation passes.
- [x] **REM-DATA-008**: `saveCategory` shall ignore any `nextFireAt` value present on the passed `Reminder` object and instead preserve, atomically with that same save (LS-BE-015), whatever `nextFireAt` is currently stored for that category — so a save can never overwrite a `nextFireAt` that `onAlarmFired` (REM-SCHED-011) updated concurrently while the edit screen was open. `nextFireAt` is written only by `ReminderScheduler` (REM-SCHED-013, REM-SCHED-014).
- [x] **REM-DATA-009**: `hasEnabledReminder()` shall emit whether any reminder is currently enabled, as a continuous stream that re-emits whenever that answer changes — including when a reminder is enabled or disabled without any category field changing, and when the last category holding an enabled reminder is deleted (REM-DATA-001). It shall be answered from the stored reminders themselves rather than derived from the category list, and shall report only whether one exists, never load them — so it reports a row stored as enabled even where decoding would demote it to disabled (REM-DATA-010), unlike `getAllEnabledRemindersOnce` (REM-DATA-007), which re-filters after decoding. Reporting one reminder too many only shows a warning banner that a real reminder would also have shown.
- [x] **REM-DATA-010**: When a stored reminder row cannot be decoded into a reminder every scheduling path can handle, the system shall yield the reminder a category with no reminder configured gets — disabled, FIXED at 09:00, all seven days — rather than letting the failure escape. Two kinds of row qualify: ones holding a field that fails to parse, such as an unrecognized mode or weekday name, or a time that is not `HH:mm`; and ones that parse cleanly into a reminder nothing downstream can use, namely one with no active days, a FIXED reminder with no times, or a RANDOM reminder with an `occurrencesPerDay` below 1. Each unusable case is scoped to the mode that reads the field, so a row is never rejected over a field its own mode ignores — a FIXED reminder decodes unchanged whatever its `occurrencesPerDay` holds. The edit screen writes none of these, but the decode runs where a thrown exception is fatal — startup reconciliation (REM-SCHED-017) decodes every enabled row on a coroutine whose failure ends the process, so one such row would crash every launch — and `computeNextFireTime`'s day-walking search does not terminate against a reminder with no active day. The decoder therefore refuses to produce an unusable reminder rather than trusting that no writer ever will. Decoding as disabled is also what keeps the row out of scheduling, since `getAllEnabledRemindersOnce` (REM-DATA-007) filters on `enabled` after decoding.

## Category Edit Integration

- [x] **REM-UI-001**: The category edit screen shall display a "Reminder" section below the Default Value fields, available for both MetaCategory and SubCategory; reminders shall not be inherited — each category's reminder configuration is independent of its parent's.
- [x] **REM-UI-002**: While a category's reminder is off, the Reminder section shall display as a single collapsed row: a reminder icon, the label "Reminder", and an off toggle.
- [x] **REM-UI-003**: While a category's reminder is on, the Reminder section shall expand to show a Mode segmented control ("Fixed time" / "Random"), an Active days row, and a "Show category name in notification" switch, always; plus mode-specific fields per REM-UI-004/REM-UI-005/REM-UI-006.
- [x] **REM-UI-004**: While Mode = Fixed, the expanded Reminder section shall display the reminder's `times` as a list of time chips (each opening a time picker on that chip's own time), a "+ Add time" control that opens a time picker on 09:00 to append another, and a tap-to-remove affordance on each chip; at least one chip shall always remain (minimum one).
- [x] **REM-UI-005**: While Mode = Random, the expanded Reminder section shall display two time-picker fields labeled "Start" and "End" for `windowStart`/`windowEnd`, both defaulting to midnight (`00:00`) until the user touches them.
- [x] **REM-UI-006**: While Mode = Random, the expanded Reminder section shall display a "Times per day" text field for `occurrencesPerDay`, requesting the numeric keyboard, holding the value as text rather than as a number so the field can be emptied and retyped, and accepting a proposed change only when the new text is empty or is one or two digits — so the field yields the range 1 to 99 and nothing outside it. Requesting the numeric keyboard is only a hint: an IME may ignore it, and a paste involves no keyboard at all. The character check is therefore what holds the range.
- [x] **REM-UI-006a**: When the user attempts to save a category whose reminder is on with Mode = Random, the system shall block the save with an error on the "Times per day" field whenever that field is empty or reads `0`, and shall report one message for both — the two differ only in how the user reached them, and in each the reminder names no number of occurrences to schedule. This error is reported on its own field, not alongside the Window error (REM-UI-009): a bad count and a bad window fail for unrelated reasons, and one shared message would name the wrong one.
- [x] **REM-UI-007**: The expanded Reminder section shall display an Active days row of 7 toggle chips (Mon–Sun), all on by default; at least one day shall remain toggled on.
- [x] **REM-UI-008**: The expanded Reminder section shall display a "Show category name in notification" switch, off by default.
- [x] **REM-UI-009**: When the user attempts to save a category whose reminder is on, the system shall block the save with an inline error unless: at least one active day is selected; if Mode = Fixed, at least one time is present; if Mode = Random, `windowEnd` (treating `00:00` as end-of-day) is after `windowStart`. The "Times per day" field carries its own precondition and its own message — see REM-UI-006a.
- [x] **REM-UI-010**: Whenever `windowEnd` is `00:00` — including, but not limited to, the untouched default where both `windowStart` and `windowEnd` are `00:00` — the system shall treat it as end-of-day, never literal start-of-day (REM-SCHED-007), so an untouched Window section is itself valid and yields a full-day window with no separate "no time chosen" affordance needed.
- [x] **REM-UI-011**: The Reminder section shall have no independent save or cancel action; its edits shall participate in the category edit screen's existing dirty-tracking and save lifecycle exactly like Name, Emoji, or Default Value — saving persists category fields and reminder config together via `saveCategory` (REM-DATA-006), and discarding via the existing unsaved-changes dialog discards reminder edits along with everything else.

## Permission Handling

- [x] **REM-PERM-001**: When the user turns on a category's reminder or opens an already-on Reminder section for editing, if `POST_NOTIFICATIONS` is not granted (Android 13+/API 33+), the system shall immediately request the runtime permission via its system dialog, proactively rather than waiting for save.
- [x] **REM-PERM-002**: While a category's reminder is switched on in the category edit screen and a reminder permission problem exists (REM-PERM-006), the system shall display an inline prompt stating that problem and offering to launch its settings screen. The prompt shall be evaluated against live permission state (REM-PERM-005) and shall stop showing once the problem is resolved, without requiring an explicit dismissal or a reopen of the screen. The prompt shall not be shown while REM-PERM-001's runtime request is awaiting an answer, since the problem it would name is the one that dialog is already asking about. This prompt is the only recovery path for a denied notification permission, which Android will not re-request after the first denial (REM-PERM-001).
- [x] **REM-PERM-003**: When the user attempts to save a category with its reminder enabled and a reminder permission problem exists at that moment (REM-PERM-006), the system shall show a blocking confirmation dialog stating that problem and offering "Save anyway"; choosing Cancel shall abort the save entirely (nothing persisted, screen remains open); choosing "Save anyway" shall proceed with the save and arm with whatever degraded behavior is available.
- [x] **REM-PERM-004**: The category list screen shall display an ambient banner, evaluated live against current permission state (not from a stored flag) whenever the set of categories with an enabled reminder changes (REM-DATA-009) or that permission state changes (REM-PERM-005), whenever at least one category has an enabled reminder and a reminder permission problem exists (REM-PERM-006); the banner shall state that problem and, when tapped, open that same problem's settings screen; it shall stop showing automatically once the problem is resolved, without requiring any explicit dismissal or state update.
- [x] **REM-PERM-005**: Any surface that displays permission state (REM-PERM-002's inline prompt, REM-PERM-004's banner) shall observe exact-alarm availability via a context-registered receiver for `AlarmManager.ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` (API 31+), and notification state — both the app-level permission and the `reminders` channel's importance, neither of which has an equivalent broadcast — via window focus, so that a change made outside the app reaches the display without requiring an activity lifecycle resume — which multi-window mode does not deliver, since every visible activity stays `RESUMED` while the user acts in an adjacent pane. Surfaces that read permission state at the moment of a user action rather than displaying it (REM-PERM-003's save-time check) shall read it directly and are outside this requirement.
- [x] **REM-PERM-006**: Where the system reports a reminder permission problem (REM-PERM-002, REM-PERM-003, REM-PERM-004), it shall report exactly one problem, selected in this order: notifications disabled for the app (`areNotificationsEnabled() == false`, any API level), then the `reminders` notification channel disabled (`getNotificationChannel(REMINDER_NOTIFICATION_CHANNEL_ID)?.importance == IMPORTANCE_NONE`), then exact-alarm scheduling unavailable (`canScheduleExactAlarms() == false`, API 31+); if none holds, there is no problem to report. Each case shall state its own consequence and link to the settings screen that fixes it: app-level notifications shall state that reminders will not be shown and link to `ACTION_APP_NOTIFICATION_SETTINGS`; a disabled channel shall state the same and link to `ACTION_CHANNEL_NOTIFICATION_SETTINGS` for that channel; unavailable exact alarms shall state that reminders may not arrive on time and link to `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`. The two notification problems rank above exact alarms because they stop the reminder being seen at all while unavailable exact alarms affect only its timing; app-level ranks above the channel because unblocking the channel while the app is muted changes nothing.

## Scheduling Engine

- [x] **REM-SCHED-001**: `computeNextFireTime(reminder, after, zone, random)` shall be a pure function that returns the next fire `Instant` strictly after `after`, taking no dependency on any stored or global state beyond its arguments.
- [x] **REM-SCHED-002**: When `enableReminder` proceeds to recompute — on first enable, or on an edit whose existing `nextFireAt` is no longer valid per REM-SCHED-018 — the system shall call `computeNextFireTime` with `after` = the current time.
- [x] **REM-SCHED-003**: When `onAlarmFired`'s reschedule runs after a reminder's alarm fires, the system shall call `computeNextFireTime` with `after` = the instant the alarm fired.
- [x] **REM-SCHED-004**: When `rearmAll()` runs (triggered by boot, system clock change, or timezone change — REM-SCHED-016), the system shall, for each enabled reminder, re-arm using its existing `nextFireAt` unchanged if it is still valid (REM-SCHED-018); otherwise it shall call `computeNextFireTime` with `after` = the current time, using the current timezone, persist the result, and arm with it.
- [x] **REM-SCHED-005**: When `reconcileOnStartup()` re-arms a reminder (REM-SCHED-017), the system shall call `computeNextFireTime` with `after` = the current time.
- [x] **REM-SCHED-006**: While `reminder.mode == FIXED`, `computeNextFireTime` shall find the earliest entry in `times` (sorted) within `after`'s local date whose instant is after `after` on an active day; if none qualifies, it shall advance date-by-date — skipping inactive days — to the next active day and use that day's earliest time.
- [x] **REM-SCHED-007**: While `reminder.mode == RANDOM`, `computeNextFireTime` shall divide `[windowStart, effectiveWindowEnd]` into `occurrencesPerDay` equal-length sub-windows, where `effectiveWindowEnd` is end-of-day (the instant before the next day's `00:00`) when `windowEnd == 00:00`, and `windowEnd` verbatim otherwise; it shall find the earliest sub-window starting later than `after` (a sub-window that `after` merely falls inside counts as already handled, not as still available) and draw one uniform-random instant within it using the injected `random` source; if no sub-window today starts later than `after`, it shall advance to the next active day and draw within that day's first sub-window.
- [x] **REM-SCHED-008**: The system shall keep exactly one alarm armed per enabled reminder at any time, never one alarm per occurrence; after an alarm fires, the receiver shall compute and arm only the single next occurrence.
- [x] **REM-SCHED-009**: Every call site that arms or cancels a reminder's alarm (initial arm, post-fire reschedule, `rearmAll()`, and `cancel()`) shall build the alarm's `PendingIntent`/`Intent` via one shared private helper, using a `data` `Uri` of the form `trackr://reminder/$categoryId` for matching purposes, so `AlarmManager`'s `Intent.filterEquals`-based matching (action/component/data/categories, not extras) replaces rather than stacks alongside any alarm already pending for that category.
- [x] **REM-SCHED-010**: The system shall arm reminder alarms via `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, nextFireAt, pendingIntent)`, falling back to `AlarmManager.setAndAllowWhileIdle()` (inexact) when `canScheduleExactAlarms() == false`.
- [x] **REM-SCHED-011**: When `ReminderReceiver` receives a fired alarm, the system shall re-read the `Reminder` row for the intent's `categoryId`; if the row is missing or `enabled` is false, it shall no-op (no notification posted, no reschedule); otherwise it shall post the notification (REM-NOTIF) unless suppressed (REM-SCHED-020), recompute `nextFireAt` via `computeNextFireTime` with `after` = the fired instant (REM-SCHED-003), persist it, and re-arm regardless of suppression.
- [x] **REM-SCHED-012**: When `ReminderScheduler.cancel(categoryId)` is called, the system shall rebuild the `PendingIntent` via the same shared helper used to arm (REM-SCHED-009) before calling `AlarmManager.cancel`, so the cancel call matches and actually cancels the pending alarm rather than silently no-op'ing on a mismatched `PendingIntent`.
- [x] **REM-SCHED-013**: When `ReminderScheduler.enableReminder(reminder)` is called — on first enable, or on any save of the category edit screen while the reminder is active, regardless of which fields changed — the system shall first re-read the reminder's current `nextFireAt` from the repository (not any value on the `reminder` argument) and check whether it is still valid under the reminder's current configuration (REM-SCHED-018); if valid, it shall leave the stored `nextFireAt` unchanged, otherwise it shall compute `nextFireAt` with `after` = the current time (REM-SCHED-002) and persist it. In both cases it shall arm the alarm for the resulting `nextFireAt` before returning — a valid stored `nextFireAt` is not evidence that an alarm is still pending for it, because force-stop, app update, and OEM task-kill all clear pending alarms while leaving the row intact, and re-arming an alarm that is already pending replaces it rather than stacking (REM-SCHED-009).
- [x] **REM-SCHED-014**: When `ReminderScheduler.disableReminder(categoryId)` is called, the system shall persist `enabled = false` and `nextFireAt = null`, and cancel the pending alarm (REM-SCHED-012).
- [x] **REM-SCHED-015**: When the user saves the category edit screen while the category's reminder is enabled, the system shall re-run `enableReminder` (REM-SCHED-013) regardless of whether any reminder-specific field (mode, window, times, active days) was the one that changed; for a `RANDOM`-mode reminder whose `nextFireAt` is still valid (REM-SCHED-018), nothing is recomputed or persisted, so saving unrelated category fields never disturbs an already-correctly-scheduled reminder or draws a new random time. The alarm is still re-armed for that unchanged `nextFireAt` (REM-SCHED-013).
- [x] **REM-SCHED-016**: When the device broadcasts `BOOT_COMPLETED`, `ACTION_TIME_CHANGED`, or `ACTION_TIMEZONE_CHANGED`, a manifest-registered `ReminderRearmReceiver` shall call `ReminderScheduler.rearmAll()`, which loads every enabled reminder (`getAllEnabledRemindersOnce`, REM-DATA-007) and re-arms each one per REM-SCHED-004.
- [x] **REM-SCHED-017**: On every app process start, the system shall run `ReminderScheduler.reconcileOnStartup()`, fire-and-forget. After the exact-alarm upgrade check (REM-SCHED-019), it shall load every enabled reminder (`getAllEnabledRemindersOnce`, REM-DATA-007) and re-arm any whose `nextFireAt` is null, or in the past by more than a buffer, recomputing from the current time (REM-SCHED-005); a reminder whose `nextFireAt` is still in the future, or in the past by less than the buffer, shall be left untouched. The buffer shall be 10 minutes when the `lastKnownExactAlarmAvailable` flag (REM-SCHED-019), as read at the start of this pass, is `true`, and 30 minutes when it is `false`.
- [x] **REM-SCHED-018**: A stored `nextFireAt` is considered valid only for `RANDOM` mode, and only when it falls within the sub-window containing the current time (the *current box*) or the sub-window immediately following it (the *next box* — the state a normal post-fire reschedule leaves things in), both computed under the reminder's current configuration. `FIXED` mode has no equivalent check — recomputing via `computeNextFireTime(after = now)` is already idempotent whenever nothing relevant changed. A `null` `nextFireAt` is never valid. This check is shared by REM-SCHED-013 (save/enable) and REM-SCHED-004 (`rearmAll()`), both of which skip recomputing — and thus avoid discarding, or worse silently skipping, a still-pending occurrence — whenever the stored value already passes it.
- [x] **REM-SCHED-019**: `ReminderScheduler` shall persist a device-wide `lastKnownExactAlarmAvailable: Boolean` flag (default `false`), independent of any individual `Reminder`. At the start of each `reconcileOnStartup()` pass (REM-SCHED-017), it shall compare a live read of `AlarmManager.canScheduleExactAlarms()` to this stored flag; on a `false → true` transition, it shall re-issue the arm call for every enabled reminder whose `nextFireAt` is non-null and not stale under REM-SCHED-017's buffer, using each one's existing, unmodified `nextFireAt` (no recompute) via the exact API, then update the stored flag to `true`. A reminder whose `nextFireAt` is null or stale shall be excluded from this walk — REM-SCHED-017's staleness pass recomputes and re-arms it instead, so including it here too would arm it a second time at a stale, possibly already-past instant. A `true → false` transition shall not be specially handled.
- [x] **REM-SCHED-021**: `ReminderScheduler` shall reach `AlarmManager` only through an injected `AlarmScheduler` interface, whose sole production implementation is `AndroidAlarmScheduler`, so that every decision it makes — whether to arm, at what instant, exactly or inexactly (REM-SCHED-009, REM-SCHED-010), and when to cancel — is exercisable in a plain unit test with no Android runtime present. Code deciding whether exact alarms are available shall ask that interface rather than calling `AlarmManager.canScheduleExactAlarms()` itself, so the decision stays reachable from those tests.
- [x] **REM-SCHED-020**: When `onAlarmFired` fires for a `FIXED`-mode reminder, the system shall suppress the notification (but still recompute and re-arm `nextFireAt` normally, per REM-SCHED-011) if the most recently logged event's timestamp for the category or any of its SubCategories (LS-BE-014) falls within the suppression window. The window begins a lookback duration before this occurrence's **scheduled** fire time — the `nextFireAt` the alarm was armed for — and ends at the instant the alarm is **delivered**, so a log made during a delayed delivery suppresses as well as one made shortly before the scheduled time. The lookback duration shall be `min(10% of the gap between this reminder's previous scheduled fire time and this occurrence's scheduled fire time, 1 hour)`, where "previous scheduled fire time" is computed by walking the reminder's `times` (sorted) and `daysActive` backward from the scheduled fire time — the mirror image of how REM-SCHED-006 walks forward — wrapping to the prior active day's last time when none of the fire date's own times qualify. The walk is anchored to the scheduled fire time rather than the delivery instant because delivery is always at or after the scheduled instant, so walking back from delivery returns the current occurrence rather than the previous one. When the reminder has no stored `nextFireAt`, the delivery instant shall be used as the scheduled fire time. `RANDOM`-mode reminders shall never be suppressed.

## Notifications

- [x] **REM-NOTIF-001**: The system shall create a single notification channel, `"reminders"`, at app startup, idempotently, with default importance.
- [x] **REM-NOTIF-002**: Every reminder notification's title shall be the generic "Time to log", regardless of `showCategoryInNotification`.
- [x] **REM-NOTIF-003**: A reminder notification's body shall default to a generic prompt ("You have a category waiting to be logged"); when the firing reminder's `showCategoryInNotification` is true, the body shall instead be "{emoji} {category name}" for that category.
- [x] **REM-NOTIF-004**: Every reminder notification shall set `setGroup("reminders")` using the same group key across every category, and the system shall post a group summary notification carrying that same key with `setGroupSummary(true)`. The summary shall open the timeline when tapped and shall set `setAutoCancel(false)`, so that tapping it leaves every reminder notification in place — the timeline's outstanding list (REM-NOTIF-008) is built from those notifications, and cancelling them would deliver the user to an empty list. The summary shall be cancelled when the last reminder notification is cancelled, so that no summary is ever shown over an empty group.
- [x] **REM-NOTIF-007**: Every reminder notification shall be posted with the category's id as its notification tag and a constant notification id, so that posting for a category replaces only that category's own previous notification. The tag is also what REM-NOTIF-008 reads to recover a category from a shown notification, so the id is carried once rather than repeated in the notification's extras.
- [x] **REM-NOTIF-005**: A reminder notification's `PendingIntent` shall target `MainActivity` with the category's id as an extra (see `docs/specs/app-shell.md § Navigation` for how `MainActivity` reads that extra and constructs `Routes.timeline(quickLogCategoryId = categoryId)`, and `docs/specs/event-logging.md § Quick-Log Sheet` for how `HomeViewModel` opens the sheet from it) so tapping it deep-links into quick-log for that category.
- [x] **REM-NOTIF-006**: The system shall not display action buttons (e.g. "Log now", "Snooze") on reminder notifications in v1; tap-to-open is the only interaction.
- [x] **REM-NOTIF-008**: A reminder shall be outstanding for exactly as long as its notification is showing, with no separate record kept. The set of outstanding reminders shall be read from the app's own currently-showing notifications, excluding any entry marked as a group summary (REM-NOTIF-004), taking each remaining entry's category from its tag (REM-NOTIF-007). It follows that dismissing a notification, or tapping it and not logging, leaves nothing outstanding for that category, and that no reminder is outstanding after a device restart, since the system clears shown notifications and none are re-posted.
- [x] **REM-NOTIF-010**: Cancelling a category's reminder — whether because the reminder was disabled or because the category was deleted — shall also cancel that category's reminder notification if one is showing, so that nothing stays outstanding for a reminder that no longer exists and the shade never advertises a deleted category.
- [x] **REM-NOTIF-011**: Every path that cancels a reminder notification shall go through one operation that cancels it and then cancels the group summary if no reminder notification remains (REM-NOTIF-004), so that the summary's lifetime is not a rule each call site has to remember.
- [x] **REM-NOTIF-009**: The set of outstanding reminders shall be held as observable state that the system updates on each event that changes it — the app posting a reminder notification, the app cancelling one, and the user dismissing one — so that a surface displaying it observes a value rather than deciding when to re-read. No surface shall re-read on its own schedule or on regaining focus: a re-read on any trigger other than an actual change would repair the list whenever it happened to run, hiding a failure of the events themselves.
- [x] **REM-NOTIF-013**: Everything that posts, cancels, or reads reminder notifications shall do so through an injected `ReminderNotifier` interface, whose sole production implementation is `AndroidReminderNotifier`, so that what is outstanding (REM-NOTIF-008) and when a notification is posted or cancelled are exercisable in a plain unit test with no Android runtime present.
- [x] **REM-NOTIF-012**: Every reminder notification, and the group summary, shall carry a delete intent that updates the outstanding set (REM-NOTIF-009) when it fires. Android fires a delete intent when the user dismisses a notification — individually, or by clearing the shade — and not when the app cancels one or when an auto-cancel follows a tap, so it reports exactly the changes the app cannot otherwise observe, and delivers even when the app is not running.
