# Reminders Specs

LLD: `docs/llds/reminders.md`

---

## Data Model

- [x] **REM-DATA-001**: The system shall store at most one `Reminder` per category (zero or one row), keyed by `categoryId`, with a foreign key to `categories(id)` declared `CASCADE DELETE`, so deleting a category automatically deletes its reminder row.
- [x] **REM-DATA-002**: A `Reminder` row shall store `enabled`, `mode` (`FIXED` or `RANDOM`), `times` (FIXED-mode clock times), `windowStart`/`windowEnd`/`occurrencesPerDay` (RANDOM-mode window config), `daysActive`, `showCategoryInNotification`, and `nextFireAt` together in one flat schema; switching `mode` shall not clear or overwrite the fields belonging to the other mode, so a user's prior configuration for a mode is preserved when they switch back to it.
- [x] **REM-DATA-003**: The Category Edit screen's reminder UI state shall default `showCategoryInNotification` to `false` for a category with no existing reminder.
- [x] **REM-DATA-004**: The Category Edit screen's reminder UI state shall default `daysActive` to all seven days for a category with no existing reminder.
- [x] **REM-DATA-005**: `nextFireAt` shall store the instant this device last armed (or attempted to arm) for the reminder's currently-pending alarm; it shall be null whenever the reminder is disabled or has not yet been armed. It is this device's own record of what it told `AlarmManager`, not a value recomputable from the reminder's configuration alone.
- [x] **REM-DATA-006**: `saveCategoryWithReminder(category, reminder)` shall persist the category's fields and its `Reminder` config (upsert, or clear when `reminder` is null) together in a single database transaction.
- [x] **REM-DATA-007**: `getAllEnabledRemindersOnce()` shall return every `Reminder` row with `enabled = true` as a one-shot (non-`Flow`) list, for use by boot/clock-change re-arm and startup reconciliation passes.
- [x] **REM-DATA-008**: `saveCategoryWithReminder` shall ignore any `nextFireAt` value present on the passed `Reminder` object and instead preserve, within the same transaction, whatever `nextFireAt` is currently stored for that category — so a save can never overwrite a `nextFireAt` that `onAlarmFired` (REM-SCHED-011) updated concurrently while the edit screen was open. `nextFireAt` is written only by `ReminderScheduler` (REM-SCHED-013, REM-SCHED-014).

## Category Edit Integration

- [x] **REM-UI-001**: The category edit screen shall display a "Reminder" section below the Default Value fields, available for both MetaCategory and SubCategory; reminders shall not be inherited — each category's reminder configuration is independent of its parent's.
- [x] **REM-UI-002**: While a category's reminder is off, the Reminder section shall display as a single collapsed row: a reminder icon, the label "Reminder", and an off toggle.
- [x] **REM-UI-003**: While a category's reminder is on, the Reminder section shall expand to show a Mode segmented control ("Fixed time" / "Random"), an Active days row, and a "Show category name in notification" switch, always; plus mode-specific fields per REM-UI-004/REM-UI-005/REM-UI-006.
- [x] **REM-UI-004**: While Mode = Fixed, the expanded Reminder section shall display the reminder's `times` as a list of time chips (each opening a `TimePicker`), a "+ Add time" control to append another, and a tap-to-remove affordance on each chip; at least one chip shall always remain (minimum one).
- [x] **REM-UI-005**: While Mode = Random, the expanded Reminder section shall display two `TimePicker` fields labeled "Start" and "End" for `windowStart`/`windowEnd`, both defaulting to midnight (`00:00`) until the user touches them.
- [x] **REM-UI-006**: While Mode = Random, the expanded Reminder section shall display a "Times per day" stepper for `occurrencesPerDay`, ranging from 1 to a fixed reasonable cap (e.g. 12).
- [x] **REM-UI-007**: The expanded Reminder section shall display an Active days row of 7 toggle chips (Mon–Sun), all on by default; at least one day shall remain toggled on.
- [x] **REM-UI-008**: The expanded Reminder section shall display a "Show category name in notification" switch, off by default.
- [x] **REM-UI-009**: When the user attempts to save a category whose reminder is on, the system shall block the save with an inline error unless: at least one active day is selected; if Mode = Fixed, at least one time is present; if Mode = Random, `occurrencesPerDay >= 1` and `windowEnd` (treating `00:00` as end-of-day) is after `windowStart`.
- [x] **REM-UI-010**: Whenever `windowEnd` is `00:00` — including, but not limited to, the untouched default where both `windowStart` and `windowEnd` are `00:00` — the system shall treat it as end-of-day, never literal start-of-day (REM-SCHED-007), so an untouched Window section is itself valid and yields a full-day window with no separate "no time chosen" affordance needed.
- [x] **REM-UI-011**: The Reminder section shall have no independent save or cancel action; its edits shall participate in the category edit screen's existing dirty-tracking and save lifecycle exactly like Name, Emoji, or Default Value — saving persists category fields and reminder config together via `saveCategoryWithReminder` (REM-DATA-006), and discarding via the existing unsaved-changes dialog discards reminder edits along with everything else.

## Permission Handling

- [x] **REM-PERM-001**: When the user turns on a category's reminder or opens an already-on Reminder section for editing, if `POST_NOTIFICATIONS` is not granted (Android 13+/API 33+), the system shall immediately request the runtime permission via its system dialog, proactively rather than waiting for save.
- [x] **REM-PERM-002**: When the user turns on a category's reminder or opens an already-on Reminder section for editing, if exact-alarm scheduling is unavailable (`AlarmManager.canScheduleExactAlarms() == false`, API 31+), the system shall display an inline prompt offering to launch the system "Alarms & reminders" settings screen (`ACTION_REQUEST_SCHEDULE_EXACT_ALARM`), since no in-app runtime dialog exists for this permission.
- [x] **REM-PERM-003**: When the user attempts to save a category with its reminder enabled and, at that moment, `POST_NOTIFICATIONS` is still not granted or exact-alarm scheduling is still unavailable, the system shall show a blocking confirmation dialog reading "Notifications aren't fully enabled — this reminder may not fire or may not be visible. Save anyway?"; choosing Cancel shall abort the save entirely (nothing persisted, screen remains open); choosing "Save anyway" shall proceed with the save and arm with whatever degraded behavior is available.
- [x] **REM-PERM-004**: The category list screen shall display an ambient banner, evaluated live against current permission state (not from a stored flag) whenever the set of categories with an enabled reminder changes or the screen resumes, whenever at least one category has an enabled reminder and either `POST_NOTIFICATIONS` is denied or `canScheduleExactAlarms() == false`; the banner shall read "Some reminders may not fire reliably — tap to review" and link to the relevant system settings screen; it shall stop showing automatically once the missing permission is granted, without requiring any explicit dismissal or state update.

## Scheduling Engine

- [x] **REM-SCHED-001**: `computeNextFireTime(reminder, after, zone, random)` shall be a pure function that returns the next fire `Instant` strictly after `after`, taking no dependency on any stored or global state beyond its arguments.
- [x] **REM-SCHED-002**: When `enableReminder` proceeds to recompute — on first enable, or on an edit whose existing `nextFireAt` is no longer valid per REM-SCHED-018 — the system shall call `computeNextFireTime` with `after` = the current time.
- [x] **REM-SCHED-003**: When `onAlarmFired`'s reschedule runs after a reminder's alarm fires, the system shall call `computeNextFireTime` with `after` = the instant the alarm fired.
- [x] **REM-SCHED-004**: When `rearmAll()` runs (triggered by boot, system clock change, or timezone change — REM-SCHED-016), the system shall, for each enabled reminder, re-arm using its existing `nextFireAt` unchanged if it is still valid (REM-SCHED-018); otherwise it shall call `computeNextFireTime` with `after` = the current time, using the current timezone, persist the result, and arm with it.
- [x] **REM-SCHED-005**: When `reconcileOnStartup()` re-arms a reminder (REM-SCHED-017), the system shall call `computeNextFireTime` with `after` = the current time.
- [x] **REM-SCHED-006**: While `reminder.mode == FIXED`, `computeNextFireTime` shall find the earliest entry in `times` (sorted) within `after`'s local date whose instant is after `after` on an active day; if none qualifies, it shall advance date-by-date — skipping inactive days — to the next active day and use that day's earliest time.
- [x] **REM-SCHED-007**: While `reminder.mode == RANDOM`, `computeNextFireTime` shall divide `[windowStart, effectiveWindowEnd]` into `occurrencesPerDay` equal-length sub-windows, where `effectiveWindowEnd` is end-of-day (the instant before the next day's `00:00`) when `windowEnd == 00:00`, and `windowEnd` verbatim otherwise; it shall find the earliest sub-window starting later than `after` (a sub-window that `after` merely falls inside counts as already handled, not as still available) and draw one uniform-random instant within it using the injected `random` source; if no sub-window today starts later than `after`, it shall advance to the next active day and draw within that day's first sub-window.
- [x] **REM-SCHED-008**: The system shall keep exactly one alarm armed per enabled reminder at any time, never one alarm per occurrence; after an alarm fires, the receiver shall compute and arm only the single next occurrence.
- [x] **REM-SCHED-009**: Every call site that arms or cancels a reminder's alarm (initial arm, post-fire reschedule, `rearmAll()`, and `cancel()`) shall build the alarm's `PendingIntent`/`Intent` via one shared private helper, using a `data` `Uri` of the form `trackr://reminder/$categoryId` for matching purposes, so `AlarmManager`'s `Intent.filterEquals`-based matching (action/component/data/categories, not extras) replaces rather than stacks alongside any alarm already pending for that category.
- [x] **REM-SCHED-010**: The system shall arm reminder alarms via `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, nextFireAt, pendingIntent)`, falling back to `AlarmManager.setAndAllowWhileIdle()` (inexact) when `canScheduleExactAlarms() == false`.
- [x] **REM-SCHED-011**: When `ReminderReceiver` receives a fired alarm, the system shall re-read the `Reminder` row for the intent's `categoryId`; if the row is missing or `enabled` is false, it shall no-op (no notification posted, no reschedule); otherwise it shall post the notification (REM-NOTIF) unless suppressed (REM-SCHED-020), recompute `nextFireAt` via `computeNextFireTime` with `after` = the fired instant (REM-SCHED-003), persist it, and re-arm regardless of suppression.
- [x] **REM-SCHED-012**: When `ReminderScheduler.cancel(categoryId)` is called, the system shall rebuild the `PendingIntent` via the same shared helper used to arm (REM-SCHED-009) before calling `AlarmManager.cancel`, so the cancel call matches and actually cancels the pending alarm rather than silently no-op'ing on a mismatched `PendingIntent`.
- [x] **REM-SCHED-013**: When `ReminderScheduler.enableReminder(reminder)` is called — on first enable, or on any save of the category edit screen while the reminder is active, regardless of which fields changed — the system shall first re-read the reminder's current `nextFireAt` from the repository (not any value on the `reminder` argument) and check whether it is still valid under the reminder's current configuration (REM-SCHED-018); if valid, it shall leave `nextFireAt` and the armed alarm unchanged. Otherwise it shall compute `nextFireAt` with `after` = the current time (REM-SCHED-002), persist it, and arm the alarm.
- [x] **REM-SCHED-014**: When `ReminderScheduler.disableReminder(categoryId)` is called, the system shall persist `enabled = false` and `nextFireAt = null`, and cancel the pending alarm (REM-SCHED-012).
- [x] **REM-SCHED-015**: When the user saves the category edit screen while the category's reminder is enabled, the system shall re-run `enableReminder` (REM-SCHED-013) regardless of whether any reminder-specific field (mode, window, times, active days) was the one that changed; for a `RANDOM`-mode reminder whose `nextFireAt` is still valid (REM-SCHED-018), this is a no-op, so saving unrelated category fields never disturbs an already-correctly-scheduled reminder or draws a new random time.
- [x] **REM-SCHED-016**: When the device broadcasts `BOOT_COMPLETED`, `ACTION_TIME_CHANGED`, or `ACTION_TIMEZONE_CHANGED`, a manifest-registered `ReminderRearmReceiver` shall call `ReminderScheduler.rearmAll()`, which loads every enabled reminder (`getAllEnabledRemindersOnce`, REM-DATA-007) and re-arms each one per REM-SCHED-004.
- [x] **REM-SCHED-017**: On every app process start, the system shall run `ReminderScheduler.reconcileOnStartup()`, fire-and-forget and not blocking the first UI frame. After the exact-alarm upgrade check (REM-SCHED-019), it shall load every enabled reminder (`getAllEnabledRemindersOnce`, REM-DATA-007) and re-arm any whose `nextFireAt` is null, or in the past by more than a buffer, recomputing from the current time (REM-SCHED-005); a reminder whose `nextFireAt` is still in the future, or in the past by less than the buffer, shall be left untouched. The buffer shall be 10 minutes when the `lastKnownExactAlarmAvailable` flag (REM-SCHED-019), as read at the start of this pass, is `true`, and 30 minutes when it is `false`.
- [x] **REM-SCHED-018**: A stored `nextFireAt` is considered valid only for `RANDOM` mode, and only when it falls within the sub-window containing the current time (the *current box*) or the sub-window immediately following it (the *next box* — the state a normal post-fire reschedule leaves things in), both computed under the reminder's current configuration. `FIXED` mode has no equivalent check — recomputing via `computeNextFireTime(after = now)` is already idempotent whenever nothing relevant changed. A `null` `nextFireAt` is never valid. This check is shared by REM-SCHED-013 (save/enable) and REM-SCHED-004 (`rearmAll()`), both of which skip recomputing — and thus avoid discarding, or worse silently skipping, a still-pending occurrence — whenever the stored value already passes it.
- [x] **REM-SCHED-019**: `ReminderScheduler` shall persist a device-wide `lastKnownExactAlarmAvailable: Boolean` flag (default `false`), independent of any individual `Reminder`. At the start of each `reconcileOnStartup()` pass (REM-SCHED-017), it shall compare a live read of `AlarmManager.canScheduleExactAlarms()` to this stored flag; on a `false → true` transition, it shall re-issue the arm call for every enabled reminder whose `nextFireAt` is non-null and not stale under REM-SCHED-017's buffer, using each one's existing, unmodified `nextFireAt` (no recompute) via the exact API, then update the stored flag to `true`. A reminder whose `nextFireAt` is null or stale shall be excluded from this walk — REM-SCHED-017's staleness pass recomputes and re-arms it instead, so including it here too would arm it a second time at a stale, possibly already-past instant. A `true → false` transition shall not be specially handled.
- [x] **REM-SCHED-020**: When `onAlarmFired` fires for a `FIXED`-mode reminder, the system shall suppress the notification (but still recompute and re-arm `nextFireAt` normally, per REM-SCHED-011) if the category's most recently logged event's timestamp falls within a lookback window immediately before the fire time. The lookback window shall be `min(10% of the gap since this reminder's previous scheduled fire time, 1 hour)`, where "previous scheduled fire time" is computed by walking the reminder's `times` (sorted) and `daysActive` backward from the fire time — the mirror image of how REM-SCHED-006 walks forward — wrapping to the prior active day's last time when none of the fire date's own times qualify. `RANDOM`-mode reminders shall never be suppressed.

## Notifications

- [x] **REM-NOTIF-001**: The system shall create a single notification channel, `"reminders"`, at app startup, idempotently, with default importance.
- [x] **REM-NOTIF-002**: Every reminder notification's title shall be the generic "Time to log", regardless of `showCategoryInNotification`.
- [x] **REM-NOTIF-003**: A reminder notification's body shall default to a generic prompt ("You have a category waiting to be logged"); when the firing reminder's `showCategoryInNotification` is true, the body shall instead be "{emoji} {category name}" for that category.
- [x] **REM-NOTIF-004**: Every reminder notification shall set `setGroup("reminders")` using the same group key across every category, relying on the OS's default same-app/same-group stacking rather than a custom summary notification.
- [x] **REM-NOTIF-005**: A reminder notification's `PendingIntent` shall target `MainActivity` with the category's id as an extra (see `docs/specs/app-shell.md § Navigation` for how `MainActivity` reads that extra and constructs `Routes.timeline(quickLogCategoryId = categoryId)`, and `docs/specs/event-logging.md § Quick-Log Sheet` for how `HomeViewModel` opens the sheet from it) so tapping it deep-links into quick-log for that category.
- [x] **REM-NOTIF-006**: The system shall not display action buttons (e.g. "Log now", "Snooze") on reminder notifications in v1; tap-to-open is the only interaction.
