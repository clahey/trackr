# Reminders

## Context and Design Philosophy

This segment owns per-category logging reminders: local notifications that prompt the user to log an event for a specific category, scheduled either at a fixed time or at a randomized time within a configurable window, one or more times a day, on user-chosen active days. It does not own the category's other fields (name/emoji/color/valueType) — those belong to `category-management` — but its configuration UI lives inside that segment's Category Edit screen.

The segment has three responsibilities: persisting reminder configuration (a thin addition to the existing Room schema), computing when a reminder should next fire (a pure, testable domain function), and driving the OS-level scheduling and notification mechanics (`AlarmManager`, a `BroadcastReceiver`, `NotificationManager`). Per `docs/high-level-design.md § Key Design Decisions`, delivery uses `AlarmManager.setExactAndAllowWhileIdle()`, one-shot with reschedule-on-fire, not `WorkManager` or `setAlarmClock()`.

## Data Model

### Reminder (domain type)

```kotlin
data class Reminder(
    val categoryId: String,
    val enabled: Boolean,
    val mode: ReminderMode,                  // FIXED or RANDOM
    val times: List<LocalTime>,              // FIXED only; one or more clock times, non-empty when mode == FIXED
    val windowStart: LocalTime,              // RANDOM only; preserved but unused while mode == FIXED (REM-DATA-002)
    val windowEnd: LocalTime,                // RANDOM only, ditto; a value of 00:00 means end-of-day, not start-of-day — see Decisions
    val occurrencesPerDay: Int,              // RANDOM only, ditto; >= 1 while mode == RANDOM
    val daysActive: Set<DayOfWeek>,          // non-empty; all 7 on a fresh reminder. ReminderScheduling.kt's day-walking loops would spin forever against an empty set — see § Decoding a stored row
    val showCategoryInNotification: Boolean, // default false, per HLD "public surfaces default to discreet" guideline
    val nextFireAt: Instant?,                // the currently-armed alarm's target instant; null when disabled or not yet armed. Written only by ReminderScheduler — saveCategory ignores this field and preserves the DB's current value (see § Data Model, § Scheduling Engine)
) {
    companion object {
        // The reminder a category has before anyone configures one: disabled, FIXED at 09:00, all
        // 7 days. The edit form seeds from it and the decoder falls back to it — see Decisions.
        fun default(categoryId: String): Reminder
    }
}

enum class ReminderMode { FIXED, RANDOM }
```

One `Reminder` per category, or none — `FIXED` mode's `times` list covers "multiple fixed times a day" (e.g. `[08:00, 20:00]`) and `RANDOM` mode's `occurrencesPerDay` covers "multiple random times a day" (e.g. 4 occurrences spread across a 9am–9pm window), so a single row per category covers every recurrence shape without needing multiple independent reminder rules.

### Storage

How a `Reminder` is stored — the columns, their types, the JSON encodings, and the foreign key — is `local-storage`'s (`docs/llds/local-storage.md § ReminderEntity`, LS-BE-072). This section owns what a reminder *means*, not how it is written down.

**Deleting a category deletes its reminder.** Storage enforces that (LS-BE-072), and it removes the row only — it does **not** cancel a live `AlarmManager` alarm, which is OS state outside the DB. That cancellation can't live inside `LocalTrackrRepository.deleteCategory()` itself — `ReminderScheduler` already depends on `TrackrRepository`, so the reverse call would be a circular dependency between segments. Instead, the **caller** of `deleteCategory` (`category-management`'s `CategoryListViewModel`/`CategoryEditViewModel`, both of which already sit above both `TrackrRepository` and can be given `ReminderScheduler` via DI) calls `repository.deleteCategory(id)` first, then `reminderScheduler.cancel(categoryId)` second — DB delete authoritative and first, OS alarm cleanup best-effort and second, mirroring `local-storage`'s existing image-deletion ordering (DB first, files after). `cancel()` rebuilds the `PendingIntent` via the same shared helper `enableReminder`/rearming use (see § Scheduling Engine), so it matches and actually cancels the pending alarm rather than silently no-op'ing on a mismatched `PendingIntent`. If the process dies between the two calls, the orphaned alarm is still safe: it fires once, `onAlarmFired`'s existence check (see § Scheduling Engine) finds no `Reminder` row and no-ops. This is a cross-segment touch into `category-management.md`'s delete flow (§ Category List Screen delete flow).

### Decoding a stored row

`ReminderEntity.toDomain()` is total. Any row it cannot turn into a reminder every scheduling path can handle decodes as `Reminder.default(categoryId)` instead. Two kinds of row reach that fallback: ones that fail to parse at all — an unrecognized `mode` or weekday name, a time that is not `HH:mm` — and ones that parse cleanly into a reminder something downstream cannot use — no active days, a FIXED reminder with no times, or a RANDOM reminder with an `occurrencesPerDay` below 1, the divisor for its sub-windows. Each unusable case is scoped to the mode that reads the field, so a row is never rejected over a field its own mode ignores.

The edit screen writes none of these, so the fallback is there for rows the app did not write: a backup restored from a different version, a downgraded build, a migration that goes wrong later. It matters because the decode runs somewhere a thrown exception is fatal — `reconcileOnStartup` decodes every enabled row on a coroutine whose only exception handler is the one that ends the process, so a single bad row would crash every launch. Decoding as disabled is also enough on its own to keep the row out of scheduling, since `getAllEnabledRemindersOnce` filters on `enabled` after decoding.

Totality is by construction rather than by enumeration: one `try` around the whole decode, with the three parseable-but-unusable cases stated as `require` calls inside it. A column added later is covered the day it appears, without anyone having to remember to guard it.

Decoding does not write, so the row stays on disk as it was and every later read reaches the same fallback — stable rather than degrading, and still readable by a future version that learns to make sense of it. It is replaced the first time the user saves that category for any reason, since the edit screen passes its reminder state to `saveCategory` on every save whether or not the reminder was touched.

### TrackrRepository additions (persistence only — no AlarmManager access)

```kotlin
fun getReminderForCategory(categoryId: String): Flow<Reminder?>
suspend fun saveReminder(reminder: Reminder)                          // upsert, standalone
suspend fun saveCategory(category: Category, reminder: Reminder? = null, ...)  // atomic: category upsert + reminder upsert; reminder.nextFireAt is ignored — the stored value is preserved. null leaves the stored reminder alone
suspend fun getAllEnabledRemindersOnce(): List<Reminder>              // boot / time-change re-arm
fun hasEnabledReminder(): Flow<Boolean>                               // drives the permission banner
```

`saveCategory` is what `CategoryEditViewModel.save()` actually calls — the category's other fields and its reminder config are edited on the same screen and saved together, so they persist atomically rather than as two independent writes that could leave a category's fields disagreeing with its reminder (`reminder = null` clears any existing reminder). The `@Transaction` that delivers that atomicity is `local-storage`'s (LS-BE-015). Arming/cancelling the `AlarmManager` alarm is **not** part of the save — it's a post-commit side effect the ViewModel triggers via `ReminderScheduler` once the save succeeds (see § Scheduling Engine), consistent with how image file deletion already happens after, not inside, `local-storage`'s writes elsewhere. `saveCategory` ignores any `nextFireAt` value present on the passed `Reminder` object and instead preserves, atomically with that same save, whatever `nextFireAt` is currently stored for that category — the edit screen never needs to track or carry it forward itself, and a save can never clobber a `nextFireAt` that `ReminderReceiver`/`onAlarmFired` updated concurrently while the screen was open (see § Scheduling Engine).

`hasEnabledReminder()` asks the banner's precondition (§ Permission handling, point 3) of the reminder store directly rather than deriving it from anything upstream, so it re-emits when and only when that answer changes.

These live in `local-storage.md`'s `TrackrRepository`/`LocalTrackrRepository`/`ReminderDao` (§ Room Entities, § DAOs, § LocalTrackrRepository).

## Category Edit Integration (UI)

A new **"Reminder"** section appears in the Category Edit screen (`category-management`'s `CategoryEditScreen`/`CategoryEditViewModel`), below the Default Value fields. Available for both MetaCategory and SubCategory — reminders are not inherited (independent per category).

**Collapsed state (reminder off):** a single row — `[Reminder icon] Reminder  [off toggle]`.

**Expanded state (reminder on):**

| Field | Input | Shown when |
|---|---|---|
| Mode | Segmented control: "Fixed time" / "Random" | Always (reminder on) |
| Times | List of time chips, each opening the shared `TimePickerDialog` (`docs/llds/event-logging.md § Time Picker Dialog`) on that chip's own time; `[+ Add time]` opens the same dialog on 09:00 to append another; tap-to-remove on each chip (minimum one) | Mode = Fixed |
| Window | Two fields, "Start" and "End", each opening the shared `TimePickerDialog`; both default to midnight until touched | Mode = Random |
| Times per day | Text field requesting the numeric keyboard, accepting digits only and at most two of them (so 1–99); may be held empty while the user retypes. The keyboard is only a hint — an IME may ignore it, and a paste involves no keyboard at all — so the character filter is what makes "digits only" true; the keyboard just spares the user hunting for the digits | Mode = Random |
| Active days | Row of 7 toggle chips (Mon–Sun), all on by default | Always (reminder on) |
| Show category name in notification | Switch, default off | Always (reminder on) |

**Validation:** at least one active day; Fixed mode requires at least one time; Random mode requires a Times per day of at least 1 and a `windowEnd` — treating `00:00` as end-of-day — after `windowStart`. Because Times per day is held as text, it has two invalid states the user can reach: empty, and `0`. Both block the save and report the same message, on the field rather than beside the Window fields — the count and the window fail for unrelated reasons and a shared message would name the wrong one. Both Window fields default to `00:00`, so an untouched Window section (`windowStart = 00:00`, `windowEnd = 00:00` read as end-of-day) is itself valid and yields a full-day window — no separate "no time chosen" affordance is needed.

**Save is atomic with the rest of the category edit.** The Reminder section has no independent save/cancel — it participates in the screen's existing dirty-tracking/save lifecycle exactly like Name, Emoji, or Default Value. Saving persists category fields and reminder config together via `saveCategory` (see § Data Model); discarding (via the existing `UnsavedChangesDialog`) discards reminder edits along with everything else.

**Permission handling.** Three separate moments, because "ask" and "warn" need different timing depending on whether a person is present to answer a dialog:

1. **On entering/expanding the Reminder section** (turning the collapsed row on, or opening an already-on one to edit): if `POST_NOTIFICATIONS` is not granted (Android 13+), the runtime permission dialog is requested immediately — proactively, not deferred to save. Whatever is still missing after that — notifications off, on any API level, or exact-alarm scheduling unavailable (`AlarmManager.canScheduleExactAlarms() == false`, API 31+) — is reported by a single inline prompt that opens the system settings screen for it, held back while the runtime dialog is still on screen so the two don't say the same thing at once. That prompt is the only recovery path either permission has: Android shows the runtime notification dialog once and silently ignores every later request after a denial, and exact alarms have no in-app dialog at all, only the system "Alarms & reminders" screen (`ACTION_REQUEST_SCHEDULE_EXACT_ALARM`).
2. **On save**, if the reminder is enabled and either permission is still missing (denied, or the user didn't act on the step-1 prompt), a confirmation dialog blocks the save, naming what is wrong and offering **Save anyway**. **Cancel** aborts the save entirely (nothing persisted, screen stays open); **Save anyway** proceeds, persisting and arming with whatever degraded behavior is available (inexact scheduling and/or a silently-dropped notification — neither `AlarmManager` nor `NotificationManagerCompat` throw for a missing permission, they degrade silently, so nothing crashes either way).
3. **Ambient, live-checked banner** (not a stored flag) on the Category List screen: shown whenever at least one category has an enabled reminder **and** something is missing at the moment the screen composes, linking to the system settings screen for whatever it names. Because it's evaluated live rather than tracked as persisted state, it self-heals once permission is granted (see *Keeping those reads live* below for what makes the re-read happen). This is the backstop for anything step 1/2 can't reach — permission missing (or later revoked) with no interactive save happening at all. It's deliberately *not* an active retry-at-startup mechanism on its own; § Scheduling Engine's startup reconciliation already retries scheduling itself on every launch, so the banner only needs to report whatever that retry couldn't fix.

**Choosing what to report.** All three moments answer the same question — given what is missing, what is wrong, what should it say, and where should the user be sent — so they share one decision, `reminderPermissionProblem(notificationsEnabled, reminderChannelEnabled, exactAlarmAvailable)` in `ui/components/PermissionState.kt`, which returns the single most severe problem or `null` when nothing is wrong.

Three problems, ranked. Two of them stop the reminder being seen at all: notifications turned off for the whole app, and the `reminders` channel turned off on its own while the app stays enabled. App-level outranks the channel, since unblocking the channel while the app is muted changes nothing. Exact alarms rank last — that reminder still arrives, just imprecisely — so reporting it while either notification problem stands sends someone to fix the smallest of the three and leaves the notice up when they come back. Wording and destination split the same way: the two notification problems say the reminder won't be shown and open app notification settings and the channel's own settings screen respectively, while exact alarms says it may arrive late and opens "Alarms & reminders". Reporting one problem at a time is deliberate — fixing the named one re-evaluates and names the next, and the more severe message is not made less true by a milder problem also being present.

The decision is a pure function so the precedence and the wording can be unit-tested without composition. `rememberReminderPermissionProblem()` wraps it over the live reads for the surfaces that sit in composition; `CategoryEditViewModel.save()` calls it directly and exposes the result as `pendingPermissionConfirmation`, so the save dialog names the same cause the inline prompt would. It asks the injected `AlarmScheduler` whether exact alarms are available rather than taking that from the screen, which is what puts the save-time decision under test; the two notification reads still arrive as parameters, having no equivalent interface to ask.

Points 1 and 3 also render the same thing — `ReminderPermissionNotice`, an error-toned row naming the problem that opens its settings screen when tapped — so a problem reads and behaves identically wherever it surfaces. Only shape and placement differ: full-bleed at the top of the category list, rounded and inline within the Reminder section.

**Keeping those reads live.** Points 1 and 3 both *display* permission state, so a change made outside the app has to reach them. Exact-alarm availability is observed through `AlarmManager`'s `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` broadcast (API 31+, context-registered), which Android sends whenever `canScheduleExactAlarms()` flips in either direction, so the prompt and the banner clear the moment the permission is granted on the system settings screen and reappear if it is revoked. Neither notification read has an equivalent broadcast, so both — app-level permission and the `reminders` channel's own importance — are re-read whenever the window regains focus. Window focus rather than an `ON_RESUME` observer: since Android 10 every visible activity in split-screen or freeform windowing stays `RESUMED`, so an app sitting beside the Settings pane receives no resume callback when the user grants a permission in the other pane and would display stale state indefinitely. All three reads live behind `rememberExactAlarmAvailable()`, `rememberNotificationsEnabled()`, and `rememberReminderChannelEnabled()` in `ui/components/`, and reach both display surfaces through `rememberReminderPermissionProblem()`.

This applies only to the two surfaces that *display* permission state. The save-time check (point 2) reads availability once, at the moment of the action, and is correct as a direct call. The banner's tap handler doesn't read at all — it opens the settings screen for the problem the banner is currently showing, so where it goes always matches what it says.

## Scheduling Engine

`ReminderScheduler` (`@Singleton`, injected with `TrackrRepository`, `AlarmScheduler`, `ReminderNotifier`, `DataStore<Preferences>`) decides when and whether to arm, and reaches the OS through two interfaces rather than touching it: `AlarmScheduler` wraps `AlarmManager`, `ReminderNotifier` wraps `NotificationManager`. They are this segment's seam onto the platform, the way `TrackrRepository` is `local-storage`'s onto the database. `AndroidAlarmScheduler` and `AndroidReminderNotifier` are their only production implementations, bound in `di/RemindersModule` along with the two system services they need. Every scheduling decision is therefore reachable from a plain unit test with no Android runtime, standing `FakeAlarmScheduler` and `FakeReminderNotifier` in their place — which is what `ReminderSchedulerTest` runs against. `LocalTrackrRepository` and Room never talk to `AlarmManager` at all; persistence and OS scheduling stay separated, matching the HLD's System Design diagram.

**`computeNextFireTime(reminder: Reminder, after: Instant, zone: ZoneId, random: Random = Random.Default): Instant`** — domain function (lives in `domain/ReminderScheduling.kt`, unit-testable via an injected `Random` for determinism), finds the next fire instant strictly after `after`. Every call site's `after` value:

| Call site | `after` |
|---|---|
| `enableReminder` (first enable, or any edit of an active reminder) | `now` |
| `onAlarmFired` reschedule | `firedAt` |
| `rearmAll()` (boot / clock / timezone change) | `now` |
| `reconcileOnStartup()` re-arm | `now` |

- **FIXED**: within `after`'s local date, find the first entry in `times` (sorted) whose instant is after `after`, on an active day; if none, advance date-by-date (skipping inactive days) to the next active day and take its earliest time. A private mirror-image helper, `computePreviousFixedFireTime`, walks the same `times`/`daysActive` backward from a given instant instead of forward — used only by the already-logged suppression check below, not by any arm/rearm path.
- **RANDOM**: divide `[windowStart, effectiveWindowEnd]` into `occurrencesPerDay` equal-length sub-windows, where `effectiveWindowEnd` is end-of-day (the instant before the next day's `00:00`) when `windowEnd == 00:00`, and `windowEnd` verbatim otherwise. Find the earliest sub-window starting later than `after` — a sub-window `after` merely falls inside counts as already handled, not as still available — and draw one uniform-random instant inside that sub-window using `random`. If no sub-window today starts later than `after`, advance to the next active day and draw within its first sub-window. (Equal-width sub-windows with one random draw each avoids the clustering that N independent draws across the whole window risk — see Decisions.) Sub-window boundaries are static, derived purely from `windowStart`/`windowEnd`/`occurrencesPerDay` — "starts later than `after`" is a direct comparison against `after`, not a decrementing count, so no separate "occurrences remaining today" state is needed or stored; `after` (always the just-fired alarm's timestamp on the reschedule path) is enough on its own to know where in the day's sequence the next draw falls.

Exactly one alarm is ever armed per enabled reminder — never one-per-occurrence. After firing, the receiver calls back into the scheduler to compute and arm the next single occurrence.

**Arming:** `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, nextFireAt.toEpochMilli(), pendingIntent)` where `pendingIntent` wraps an `Intent` targeting `ReminderReceiver` carrying `categoryId` as an extra (read by the receiver as documented below) and, for matching purposes only, `.setData(Uri.parse("trackr://reminder/$categoryId"))` — `PendingIntent`/`AlarmManager` matching is based on `Intent.filterEquals` (action/component/data/categories), not extras, so the `data` `Uri` is what makes each arm call replace, not stack alongside, any alarm already pending for that category (see Decisions). This exact `Intent` shape is built by one shared private helper, used identically by every call site that arms or cancels a reminder's alarm (initial arm, the post-fire reschedule below, `rearmAll()`, and `cancel()`) — `cancel()` in particular only cancels the right alarm if its `PendingIntent` matches bit-for-bit what armed it. Falls back to `AlarmManager.setAndAllowWhileIdle()` (inexact) when `canScheduleExactAlarms() == false`.

**`ReminderReceiver` (BroadcastReceiver):** on receipt, reads `categoryId` from the intent and calls `ReminderScheduler.onAlarmFired(categoryId)`, which first re-reads `getReminderForCategory(categoryId)` and checks it's still non-null **and** `enabled` — a defensive existence check against the category (and its cascade-deleted `Reminder` row) having been removed, or the reminder having been disabled, since the alarm was armed. If either check fails, it's a no-op: no notification, no reschedule. Otherwise, unless suppressed (see below), it posts the notification (see § Notifications); regardless of suppression it recomputes `nextFireAt` via `computeNextFireTime(reminder, after = firedAt, ...)`, persists it, and re-arms. This check is a safety net alongside — not a replacement for — the explicit `ReminderScheduler.cancel(categoryId)` call `deleteCategory` needs to make (see § Data Model): the explicit cancel avoids uselessly waking the device for an alarm that's already known to be moot, while this check covers any case that cancel doesn't reach (a disable racing a fire, most notably — see Decisions).

**Already-logged suppression (FIXED mode only).** A `FIXED`-mode reminder fires at a fixed clock time regardless of whether the user already logged the category on their own beforehand — annoying when they did. `onAlarmFired` reads the latest event timestamp for the category and its SubCategories (`repository.getLatestEventTimestampIncludingChildren(categoryId)`, a single `MAX` aggregate — the fire path runs on a Doze wakeup inside the receiver's `goAsync()` budget, and is skipped entirely for RANDOM, which cannot suppress) and, if that timestamp falls within the suppression window, skips posting the notification (the reschedule/re-arm above still happens exactly as normal — this only affects whether *this* occurrence's notification is shown). Two instants matter here and they are not the same: `scheduledAt`, the `nextFireAt` this alarm was armed for (read off the reminder row before the reschedule overwrites it, falling back to `firedAt` when the row holds none), and `firedAt`, when the alarm was actually delivered. Delivery is always at or after the scheduled instant — by milliseconds under an exact alarm, by hours under the `setAndAllowWhileIdle` fallback in Doze. The window runs from `scheduledAt` minus a lookback duration through `firedAt`, so it catches both a log made shortly before the reminder was due and one made while a delayed delivery was still pending. The lookback duration is sized relative to this reminder's own schedule rather than being a fixed constant, so it scales sensibly whether times are minutes or many hours apart: `min(10% of the gap between the previous scheduled fire time and `scheduledAt`, 1 hour)`. "Previous scheduled fire time" is computed the same way `computeNextFireTime` computes the *next* one, just walking `times` (sorted) backward instead of forward, wrapping to the prior active day's last time when none of the date's own times qualify. That walk pivots on `scheduledAt`, never on `firedAt`: the backward walk qualifies candidates strictly before its pivot, and `scheduledAt` is itself one of the reminder's scheduled times, so pivoting on the delivery instant would return the occurrence being delivered rather than the one before it — collapsing the gap, and with it the lookback, to the delivery jitter — so a reminder with `times = [08:00, 20:00]` gets a 12-hour gap — 10% would be 72 minutes, but the 1-hour cap applies, giving a 60-minute window before each fire (a 08:05 log doesn't suppress the 20:00 fire; a 19:55 log does suppress it); a tighter schedule like `times = [08:00, 09:00]` gets an uncapped 6-minute window (10% of the 1-hour gap). A single once-daily time gets a 24-hour gap, also capped to 1 hour rather than the uncapped 2.4 hours a flat 10% would give. `RANDOM`-mode reminders are never suppressed — an already-logged mood/symptom entry doesn't imply the next randomly-timed nudge is redundant the way a fixed clock-time one does.

**Re-arming outside normal fire-and-reschedule.** Alarms don't survive reboot, and a fixed `nextFireAt: Instant` can land at the wrong local wall-clock time if the system clock or timezone changes underneath it (e.g. travel, DST). A single `ReminderRearmReceiver` (BroadcastReceiver registered in the manifest, not dynamically — `BOOT_COMPLETED`, `ACTION_TIME_CHANGED`, and `ACTION_TIMEZONE_CHANGED` are all exempt from the implicit-broadcast background restrictions, so a manifest-registered receiver still receives them while the app isn't running) handles all three triggers identically: call `ReminderScheduler.rearmAll()`, which loads `getAllEnabledRemindersOnce()` and, for each, re-arms — preserving the stored `nextFireAt` unchanged if it's still valid (REM-SCHED-018, the same check `enableReminder` uses below), otherwise recomputing it from `after = now` in the *current* zone (never the stale pre-change value). Re-arming happens either way, since alarms don't survive reboot regardless of whether `nextFireAt` itself needed to change; skipping the recompute when the stored value is still valid avoids the same silent-skip failure mode the validity check exists to prevent at save-time (see Decisions) — recomputing unconditionally while `now` sits inside the already-armed box would treat that box as already handled and jump past a still-pending occurrence, which a routine daytime reboot could otherwise trigger silently.

**Startup reconciliation.** In addition to the broadcast-driven re-arms above, every app process start also runs a lightweight self-healing pass: `ReminderScheduler.reconcileOnStartup()`.

It first computes the staleness buffer: 10 minutes if the stored `lastKnownExactAlarmAvailable` flag (read at the start of this pass) is `true`, 30 minutes if `false` — matching the scheduling mode every currently-armed alarm was actually armed under (see Decisions). The buffer exists because delivering a reminder's own alarm can cold-start the app process to invoke `ReminderReceiver` — and `Application.onCreate()`, which launches this pass, always completes before Android then instantiates and calls the receiver — so an immediate-past threshold would routinely race the very fire this pass was woken up to help deliver, redoing `onAlarmFired`'s own reschedule concurrently with it.

It then loads `getAllEnabledRemindersOnce()` and, for each enabled reminder, in a single pass: if `nextFireAt` is null or stale (past the buffer above), it recomputes from `after = now` exactly like `enableReminder`'s fallback path, persists it, and arms it (REM-SCHED-017). Otherwise — the `nextFireAt` is still fresh — it checks for an exact-alarm permission upgrade: `ReminderScheduler` persists a device-wide `lastKnownExactAlarmAvailable: Boolean` flag (default `false`, independent of any individual `Reminder`) in the shared `DataStore<Preferences>`; comparing the live read above against this stored flag, on a `false → true` transition it re-issues the arm call using the still-fresh `nextFireAt` unchanged (no recompute — a harmless replace, per Arming above) via the now-available exact API (REM-SCHED-019). A null-or-stale `nextFireAt` always takes the first branch, never the second, so a stale reminder is never armed twice in one pass — once at its stale, possibly already-past value (which `setExactAndAllowWhileIdle` can deliver almost immediately, risking a spurious fire), then again at a freshly recomputed one. This is the only path that upgrades an already-armed inexact reminder to exact scheduling — `rearmAll()` and every fresh `enableReminder` call already check permission live at arm time (Arming above), so only a reminder neither of those touches (one sitting untouched with an already-valid `nextFireAt`) needs it. A `true → false` transition (permission revoked) isn't specially handled: already-armed alarms are unaffected, and anything touched thereafter naturally falls back to inexact. The `lastKnownExactAlarmAvailable` flag itself is updated once, after the pass over all reminders completes.

This is launched fire-and-forget from `TrackrApplication.onCreate()`, alongside — but not folded into — the existing `repository.onStartup()` call: `onStartup()` stays scoped to its documented purpose (image orphan cleanup, per `LS-BE-041`), and `ReminderScheduler` owns its own startup hook rather than becoming a second responsibility bolted onto `local-storage`'s. Neither blocks the first UI frame. This is a cross-segment touch into `app-shell.md` (§ Application Class).

**Enable/disable/edit:** `ReminderScheduler.enableReminder(reminder)` is called on first enable and on every save of the category edit screen while the reminder is active — regardless of which fields the save actually changed (persistence of the `Reminder` row itself already happened via `saveCategory`, which preserves the DB's current `nextFireAt` regardless of what the save's `Reminder` object carries; see § Data Model). Before recomputing anything, `enableReminder` re-reads the reminder's current `nextFireAt` from the repository — not any value on the `reminder` argument it was called with — and checks whether it is still valid under the reminder's now-current configuration; reading fresh at decision time, rather than trusting a value that may have been captured earlier, closes the same class of race the persistence-layer guarantee above closes for the save itself:

- **RANDOM mode:** valid when `nextFireAt` falls within the sub-window containing the current time (the *current box*) or the sub-window immediately following it (the *next box* — where a normal post-fire reschedule always leaves things, since the box that just fired is, from the new `now`, the current box, and the reschedule always picks the very next one). If valid, `nextFireAt` is left untouched — no DB write, no recompute. This is what keeps editing an unrelated field (name, emoji, color) on an already-correctly-armed RANDOM reminder from either drawing a fresh random instant or — worse — silently skipping today's still-pending occurrence (recomputing with `after = now` while `now` sits inside the current box would treat that box as already-handled per its own rule and jump straight to the next one).
- **FIXED mode:** no equivalent check is needed — recomputing via `computeNextFireTime(after = now)` is already idempotent whenever nothing relevant changed, since each fixed time is an exact point rather than a window.
- A missing (`null`) `nextFireAt` — first enable, or a reminder just re-enabled after being off — is never valid.

When the check fails (or there's nothing to check), `enableReminder` computes `nextFireAt` from `after = now` and persists it. Either way it ends by arming the resulting instant. The validity check governs whether the *occurrence* is recomputed, not whether an alarm is pending for it: force-stop, app update, and OEM task-killers all clear pending alarms while leaving the row untouched, and `reconcileOnStartup` won't heal that — it only re-arms a `nextFireAt` that is null or stale, so a still-future one stays silently unarmed. Arming unconditionally costs one binder call and replaces rather than stacks (§ Arming).

`disableReminder(categoryId)` persists `enabled = false, nextFireAt = null` and cancels the pending alarm via `AlarmManager.cancel(pendingIntent)`.

## Notifications

**Channel:** one notification channel, `"reminders"`, created at app startup (idempotent) with default importance.

**Content:** title is always generic — "Time to log" — regardless of `showCategoryInNotification`. Body defaults to a generic prompt ("You have a category waiting to be logged"); when `showCategoryInNotification` is true, body becomes "{emoji} {category name}" instead. This follows the HLD's "public surfaces default to discreet" guideline — showing the category is opt-in per reminder, off by default.

**Grouping:** each reminder notification sets `setGroup("reminders")` (the same key for every category), and the app posts a group summary alongside them carrying `setGroupSummary(true)` and the same key. The summary's tap opens the timeline — where the outstanding list is — and it sets `setAutoCancel(false)`, so tapping it leaves the group standing. That matters because the list the tap leads to is built from those very notifications; cancelling them on the way in would empty it. The summary is posted whenever a reminder notification is, and cancelled when the last child is cancelled, so a summary never lingers over an empty group. That last rule lives in one operation on `ReminderNotifier` — cancel this category's notification, then drop the summary if nothing remains — rather than at each of the three sites that cancel: the receiver, a tapped outstanding row, and `ReminderScheduler.cancel`. Three call sites can each forget it independently; one can't.

**Cancelling.** `ReminderScheduler.cancel(categoryId)` cancels the category's notification as well as its alarm, so disabling a reminder or deleting its category leaves nothing outstanding for a reminder that no longer exists. Deleting a category already routes through here (`category-management.md`), and without this the shade would keep advertising a category the user has removed — nothing else dismisses an already-posted notification.

**Identity:** each notification is posted under `notify(tag = categoryId, id = 0, …)`. The tag carries per-category identity — posting replaces that category's own previous notification and nothing else — and reading it back is how the outstanding list recovers a category from a shown notification.

**Outstanding reminders:** a reminder is outstanding for exactly as long as its notification is showing. The timeline lists them, read from `getActiveNotifications()` — the app's own notifications only, no listener permission involved — dropping any entry carrying `FLAG_GROUP_SUMMARY` and taking `categoryId` from each remaining entry's tag. There is no stored list: swiping a notification away, or tapping it and declining to log, ends the reminder in both places at once because there is only one place. `getActiveNotifications()` is a point-in-time read rather than a stream, so `ReminderNotifier` keeps the answer in a `StateFlow` and re-reads on each event that could change it. Surfaces observe that value; none of them decides when to look.

Three things change the shade, and each announces itself. The app posting and the app cancelling are direct — the receiver that posts runs in this process against the same singleton notifier, so nothing observes the OS to learn them. The third, the user dismissing a notification by swipe or by clearing the shade, arrives through `setDeleteIntent`: Android fires it on user dismissal and not on a programmatic cancel or an auto-cancel, so it reports exactly the case the app cannot otherwise see, and it starts the process to deliver if the app is not running.

The delete intent's handler re-reads the shade rather than removing the notification it names, and the summary carries one too. That is what makes dismissing the collapsed group safe without knowing whether Android fires the children's delete intents or only the summary's: either way at least one fires, the re-read sees a shade with no reminders left in it, and the list empties. A handler that removed only the notification it was told about would depend on that answer.

The `StateFlow` holds only what the shade currently shows. It is a view of OS state, not a record the app keeps — nothing survives the process, and after a reboot it starts empty because the shade does. Acting on a row does exactly what tapping its notification does: opens quick-log at that category's `QuickLogTarget` and cancels the notification. After a reboot the list is empty, because Android clears the shade and nothing re-posts.

**Tap action:** the notification's `PendingIntent` launches `MainActivity` carrying the category's id as an extra, with a per-category `data` `Uri` (`trackr://reminder/$categoryId`, the same identity technique as the alarm `PendingIntent` — see § Scheduling Engine's "One alarm per category" row) so one category's tap target can't clobber another's still-visible notification. `MainActivity` reads that extra and constructs `Routes.timeline(quickLogCategoryId = categoryId)` itself (`app-shell.md § MainActivity`/`§ Navigation Graph`). `HomeViewModel` consumes that argument once on init and opens the quick-log sheet **directly** at an explicit target — `event-logging.md`'s `QuickLogTarget` — independent of `ActiveFilter`, rather than going through the chip-tap-driven opening path used for in-session taps:

```kotlin
sealed class QuickLogTarget {
    data class DrillDown(val meta: Category.MetaCategory) : QuickLogTarget()  // opens straight into the drill-down view
    data class DirectEntry(val category: Category) : QuickLogTarget()        // opens straight to step 2
}
```

- **MetaCategory reminder, has SubCategories** — opens `QuickLogTarget.DrillDown(meta)` (the drill-down view: back-button header, "Log to [Name] directly" tile, SubCategory grid). **Separately**, and only for this case, that same init-time handling also sets `ActiveFilter.TopLevel(meta)` on `HomeViewModel` — a normal, permanent filter change, the same call a chip tap makes, not a temporary state tied to the dialog's lifetime. It's set "behind" the sheet: it doesn't drive what the sheet shows (the `DrillDown` target already did that directly) and needs no clearing afterward, since it was never a special transient state to begin with — once the sheet closes, the timeline is simply left filtered to that group, exactly as if the user had tapped the chip themselves before opening the FAB.
- **MetaCategory reminder, no SubCategories** — opens `QuickLogTarget.DirectEntry(category)`. `ActiveFilter` is left untouched entirely — nothing is read or written.
- **SubCategory reminder** — opens `QuickLogTarget.DirectEntry(category)`. `ActiveFilter` is left untouched entirely.

Decoupling "what the sheet opens to" (always explicit, via `QuickLogTarget`) from "what the timeline's filter is" (touched only for the one case where it's actually wanted) avoids needing any new "temporarily override, then clear" lifecycle — the two non-sticky cases simply never touch `ActiveFilter`, so there's nothing to clear. `QuickLogTarget`, `HomeViewModel`'s `quickLogCategoryId` argument, and the `ActiveFilter.TopLevel(meta)` side effect are specced in full in `event-logging.md § Quick-Log Sheet`; the deep-link wiring that gets the argument there is specced in `app-shell.md`.

**No action buttons (Log now / Snooze) in v1** — tap-to-open covers the primary flow; see Open Questions.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| Malformed stored reminders | One `try` around the whole of `toDomain()`, falling back to `Reminder.default(categoryId)`, with the parseable-but-unusable cases stated as `require` calls inside the same `try`; the stored row is left alone | Repairing each field in place, keeping whatever else on the row was readable; letting the decode throw and handling it at each call site; rewriting the row with the repaired values | Per-field repair is an enumeration, correct only until the next column is added — the `try` covers a new field the day it appears. What per-field repair buys, salvaging the readable fields off a bad row, is worth little: the row decodes as disabled either way, and the only thing that reads those fields again is the edit screen, which substitutes its own values over empty ones anyway. Handling it at the call sites means every caller repeating it, and one of the callers is a startup coroutine where a miss is a crash on launch. Rewriting the row would put a write inside a `Flow` on the read path; active repair, if it is ever wanted, belongs in `onStartup()` next to the orphaned-image cleanup |
| Where a fresh reminder's values are written | A `Reminder.default(categoryId)` factory on the companion; callers `copy()` from it | Default arguments on `Reminder`'s constructor; a `default()` taking every field as a defaulted parameter; `ReminderUIState`'s constructor defaults | Constructor defaults would stop the compiler catching a field a construction site forgot. That is worst on the save path: `ReminderUIState.toReminder()` builds the row that gets persisted, so a field added to `Reminder` and not wired through would silently reset on every save instead of failing to compile. A named function gives one place to read the values without giving that up. Taking every field as a defaulted parameter restates all ten names twice, once as parameters and once as arguments, to save callers a `copy()` |
| Times per day input | A text field the user types a number into, holding text rather than a number, filtered to at most two digits and checked at save | A picker that cannot express a bad value at all — a menu of 1 through 99, or a −/+ pair | Typing "12" is two keystrokes; the same value is a long scroll in a 99-item menu and eleven taps on a `+`. Holding text is what makes the field editable at all: a number-backed field has no way to represent the empty box you pass through when replacing a value, so it springs back to the old number instead of clearing. The two-digit filter is what keeps that freedom cheap — the only bad values left to catch are empty and `0`, which one message at save covers |
| Reminders per category | Exactly one (zero-or-one `Reminder` row) | Multiple independent reminder rules per category | `times`/`occurrencesPerDay` already cover "more than once a day" within one row; a second axis of multiple rows adds real schema/UI cost for marginal extra flexibility |
| Reminder storage shape | Separate `ReminderEntity` table, one row per category, FK → `categories(id)` CASCADE DELETE | Columns embedded directly on `CategoryEntity` | Most categories won't have a reminder configured, and the shape needs ~9 mostly mode-conditional, nullable columns — embedding would bloat the high-traffic `categories` table with columns null in the common case, and couple reminders' schema evolution to categories' migration history. A separate table also matches segment ownership (`reminders` doesn't own the category's other fields) and still gets atomic combined saves via `saveCategory`'s single transaction, and automatic cleanup via CASCADE DELETE — so splitting costs only a join to read both together, no loss of the "one save" or "one delete" ergonomics |
| Reminder mode representation | Single flat `Reminder`/`ReminderEntity` shape holding both modes' fields together (`times` for FIXED; `windowStart`/`windowEnd`/`occurrencesPerDay` for RANDOM), each preserved but unused while the other mode is active | Polymorphic `Reminder` (sealed class per mode), normalized into per-mode subtype tables (table-per-subtype) so no field is present-but-unused for a sibling mode | A subtype split forces a choice on every mode switch: either the inactive mode's values are dropped (switching Fixed → Random → Fixed loses the user's previously-configured times) or the app keeps an orphaned inactive-mode row around and merges it back in — which is exactly the data the flat shape already holds, just relocated behind a join and explicit child-row lifecycle management on every mode change. The flat shape lets a user flip between Fixed and Random while editing and get their prior config back for whichever mode they're not currently on, at the cost of a few fields unused by the sibling mode — an acceptable trade at this table's scale (one row per category, always read/written whole, never queried by mode-specific column) |
| Mode-specific field nullability (`times`, `windowStart`, `windowEnd`, `occurrencesPerDay`) | `NOT NULL` at both the domain `Reminder` and `ReminderEntity` levels; no type carries a constructor/column default — the values (`[09:00]`, `00:00`, `00:00`, `1`) that end up populating a new reminder come from `Reminder.default()` | Nullable (`LocalTime?`/`Int?`/`String?`), representing "not applicable to the current mode" literally | The only writer (`ReminderUIState.toReminder()`) populates every field on every save regardless of mode, so nullability defends against a case the app never produces — at the cost of a `!!` at every read site in `ReminderScheduling.kt`, or a `?:` in the decoder that can only ever take one branch. `nextFireAt` stays nullable because it is the one field where null is a state something writes on purpose: not armed |
| Disabling a reminder | `enabled: Boolean` field; `disableReminder` sets `enabled = false, nextFireAt = null` and cancels the alarm, row otherwise untouched | Delete the `ReminderEntity` row to represent "off" | Disabling is meant to be a reversible toggle, not a reset — deleting the row would lose the configured mode/times/window/days, forcing the user to reconfigure from scratch on re-enable. Row presence is already spoken for by CASCADE DELETE (it means "this category still exists"); overloading it to also mean "temporarily off" would conflate the category's lifecycle with the reminder's on/off state. Keeping the row also gives the Category Edit screen somewhere to read a disabled-but-configured reminder's fields from |
| Availability window scope | Per-reminder (`windowStart`/`windowEnd` on the `Reminder` itself) | One global app-wide quiet-hours setting | Different categories plausibly want different windows (an exercise reminder in the evening, a mood check any waking hour); a single global window can't express that |
| Reminder inheritance | Independent per category, no inherit toggle | Inheritable like color/emoji/valueType | Reminders are a behavior tied to how the user wants to be nudged about a specific category, not a display trait; an "inherited random window" is a confusing concept for a field no one else in the hierarchy shares |
| Multi-occurrence random spacing | Divide the window into `occurrencesPerDay` equal sub-windows, one random draw per sub-window | N independent uniform draws across the whole window | Independent draws can cluster (two picks minutes apart, a long gap elsewhere); equal sub-windows guarantee spread while keeping each individual pick genuinely random |
| Scheduling separation | `ReminderScheduler` (new component) owns all `AlarmManager` calls; `TrackrRepository`/Room only persist `Reminder` rows | AlarmManager calls inside `LocalTrackrRepository` | Keeps `local-storage` a pure persistence layer, consistent with its existing scope (Room + `ImageStore`, no OS scheduling APIs) |
| Exact-alarm permission denial | Fall back to inexact (`setAndAllowWhileIdle`) scheduling, still create/arm the reminder, surface a warning in the UI | Block reminder creation until permission granted | Matches the app's existing graceful-degradation pattern for permissions (no `CAMERA` permission required for photos); a denied optional permission shouldn't disable an otherwise-working feature |
| Overnight (midnight-crossing) window | Not supported in v1 — `windowEnd` must be after `windowStart` same day | Support wrap-around windows (e.g. 10pm–2am) | Adds real complexity (date-boundary handling in `computeNextFireTime`) for a use case not yet requested; validation simply rejects it for now |
| Window field defaults / optionality | No separate "unset" state — both `TimePicker`s simply default to `00:00`; `windowStart = 00:00` reads literally as start-of-day, `windowEnd = 00:00` is reserved to mean end-of-day (never literal start-of-day, since a same-day, non-wrapping window can never legitimately end at the day's first instant) | Nullable `windowStart`/`windowEnd` with explicit "no start time"/"no end time" checkboxes | A `TimePicker` has no native way to represent "no value," so genuine optionality would need two extra checkboxes for a rarely-needed case (leaving the window open-ended at one side). Reusing `00:00` as a meaningful sentinel — unambiguous for `windowEnd` since that literal value is otherwise always invalid — gets the same "defaults to the whole day" outcome from the picker's ordinary resting state, with no extra UI and no new nullable-within-`RANDOM`-mode state to track |
| Category save + reminder save | Combined, atomic (`saveCategory`, one transaction) | Independent saves (reminder section has its own save/cancel) | Both are edited on the same screen in the same sitting; two independent saves would need their own separate dirty-tracking and could partially fail, leaving fields and reminder config out of sync |
| Alarm/notification permission UX | Three-tier: proactive ask on entering the Reminder section; a blocking "Save anyway?" confirmation on save if still missing; an ambient, live-checked (not stored) banner on the category list for anything missed by the first two, backed by an active startup reconciliation retry rather than a passive banner alone | Single inline warning at enable time only; block reminder creation until granted; banner with no active retry behind it | A single ask-at-enable-time moment misses permission revoked later or missing before the user ever opens the reminder UI (e.g. right after install); live-checking the banner instead of storing a flag means it self-heals the moment permission is granted; retrying at every startup (not just relying on the banner to prompt a manual fix) recovers automatically the moment permission is actually granted, with the banner only reporting what the retry still can't fix |
| Notification tap target and filter stickiness | A dedicated `QuickLogTarget` opens the sheet directly, decoupled from `ActiveFilter`; only the MetaCategory-with-children case *also* sets `ActiveFilter.TopLevel(meta)`, as a normal permanent filter change, not a temporary one | Reuse the existing `ActiveFilter`-driven opening path for all three cases, setting a filter transiently and clearing it back to `All` when the sheet closes for the two non-sticky cases | A transient-filter-plus-clear-on-close design needs new "this filter is temporary" tracking and a new clear-on-close hook that doesn't exist today; a direct target sidesteps both — the sheet's content is never inferred from filter state, and the two cases that shouldn't touch the filter simply never do, so there's nothing to undo |
| One alarm per category | `PendingIntent`'s `Intent` carries a `data` `Uri` derived from `categoryId` (`trackr://reminder/$categoryId`), built by one shared helper used by every arm/cancel call site, so `AlarmManager` replaces the previous pending alarm for that category in place (`PendingIntent` matching is `Intent.filterEquals` — action/component/data/categories — not extras, so `data` is what carries per-category identity) | `categoryId.hashCode()` as the request code instead of a `data` `Uri`; explicitly `cancel()` the previous alarm before every `set*` call; track armed state in the DB and reconcile at fire time | A `hashCode()`-derived request code risks a 32-bit collision silently merging two different categories' alarms (unlikely at this app's scale, but an exact-string `data` `Uri` removes the risk entirely rather than just shrinking it, for the same cost). Relying on `PendingIntent` equality needs no extra bookkeeping and no extra `AlarmManager` call beyond the arm/cancel already needed — replacement is atomic and automatic. An explicit cancel-then-arm would be redundant given a matching `Intent` already guarantees replacement, and cleaning up duplicates only at fire time isn't viable here: two independently-valid alarms for the same still-enabled category would both pass `onAlarmFired`'s existence/`enabled` check and both fire, so correctness has to come from preventing the duplicate arm in the first place, not from filtering it out after |
| Missed/raced fire safety net | `onAlarmFired` re-reads the `Reminder` row and checks `enabled` before posting or rescheduling, in addition to the delete flow's explicit alarm cancel | Rely solely on explicit cancellation (delete, disable) to prevent stale fires | Cancellation and a concurrent fire can race (disable, or a delete, happening at the instant the alarm fires); a read-before-acting check in the receiver closes that race without needing to make cancellation itself atomic with the OS alarm state |
| Clock/timezone change handling | A manifest-registered receiver on `BOOT_COMPLETED` + `ACTION_TIME_CHANGED` + `ACTION_TIMEZONE_CHANGED`, all routed to the same "recompute every enabled reminder's `nextFireAt` from now and re-arm" path | Only re-arm on boot; leave time/timezone changes unhandled | A fixed `Instant` alarm doesn't move with the wall clock — without this, travel or a DST transition silently shifts every reminder's *local* fire time until it happens to fire once and reschedule itself |
| Notification `PendingIntent` identity | Same `data`-`Uri` technique as the alarm `PendingIntent` (`trackr://reminder/$categoryId`, constant request code `0`) | `categoryId.hashCode()` as the request code — the same alternative already rejected for alarms, see "One alarm per category" | The same collision argument in "One alarm per category" applies: a hash-derived request code risks one category's notification tap silently opening another's |
| Notification tray identity | `notify(tag = categoryId, id = 0, …)` — the string tag carries identity, the id is a constant | `categoryId.hashCode()` as the notification id; keeping the hashed id and putting the category id in the notification's extras for the outstanding list to read | The tag is an exact string, so it removes the 32-bit collision risk a hashed id only shrinks — one category's tray entry can no longer replace another's. Extras would serve the outstanding list equally well and are readable from a `StatusBarNotification`, but the tag is wanted for identity regardless, and reading the id from it keeps the notification carrying that id once instead of in two places that can disagree |
| Keeping the outstanding list current | Hold it in a `StateFlow` the notifier updates on every change, with user dismissals arriving via `setDeleteIntent` | Re-read the shade whenever a displaying surface regains window focus; keep that focus re-read as a backstop alongside the events | Focus is not when the shade changes — it misses a reminder arriving while the timeline is being looked at, and reports a dismissal only once the user has left and come back. Keeping it as a backstop is worse than not having it: it silently repairs the list, so a real failure in the event path shows up as staleness that heals whenever you glance away, which is close to undiagnosable. Every change now has a mechanism that names it, and if one breaks, the list stays wrong where someone can see it |
| Notification grouping | A real group summary, `setAutoCancel(false)`, tapping through to the timeline | Rely on the OS's default same-app/same-group stacking with no summary; a summary that auto-cancels | Without a summary, the bundle Android generates for two or more notifications has no content intent, so tapping the collapsed group does nothing at all — the app looks broken exactly when several reminders are waiting. Auto-cancel on the summary would be worse than useless here: the tap leads to a list built from those notifications, so cancelling them on the way in delivers the user to an empty screen |
| Alarm cancellation on category delete | Ordered as a caller-side sequence in `category-management`'s delete flow: `repository.deleteCategory(id)` first, `reminderScheduler.cancel(categoryId)` second | Cancel the alarm inside `LocalTrackrRepository.deleteCategory()` itself | `ReminderScheduler` already depends on `TrackrRepository`; having `local-storage` call back into `reminders` would be a circular dependency between segments. DB-delete-first mirrors this repository's existing image-deletion ordering, and is safe if interrupted because of the missed/raced-fire safety net above |
| Preserving `nextFireAt` across unrelated category edits | Before recomputing on any save of an active reminder, check whether the stored `nextFireAt` still falls in the current-or-next sub-window (RANDOM mode) under the edited config; leave it untouched if so | Always recompute from `now` on every edit of an active reminder (original design) | The original design both re-randomized RANDOM-mode reminders on every unrelated field edit (name/emoji/color) and, more seriously, could silently skip today's still-pending occurrence entirely: recomputing with `after = now` while `now` sits inside the already-armed sub-window treats that window as "already handled" (per the RANDOM algorithm's own rule) and jumps to the next one. FIXED mode needs no equivalent guard — recomputing from `after = now` is already idempotent there |
| Preserving `nextFireAt` across `rearmAll()` | Before recomputing on each `rearmAll()` pass, check whether the stored `nextFireAt` is still valid (REM-SCHED-018, the same check REM-SCHED-013 uses); leave it untouched — still re-arming with it — if so | Always recompute from `now` on every `rearmAll()` pass (original design) | The original design carried the same latent bug the save-time check above was introduced to prevent, just reachable from boot/clock-change instead of a save: recomputing with `after = now` while `now` sits inside the already-armed box treats that box as already handled and skips it, so a routine daytime reboot could silently cancel a RANDOM reminder's still-pending occurrence for the rest of the day. `rearmAll()` always re-arms regardless (alarms don't survive reboot) — only the recompute is skipped when the existing value is still good |
| `nextFireAt` integrity during concurrent saves | `saveCategory` ignores any `nextFireAt` on the passed `Reminder` object and preserves the DB's current value within the same transaction; `enableReminder` re-reads `nextFireAt` from the repository at decision time rather than trusting any value passed to it | Have the UI/ViewModel carry the loaded `nextFireAt` forward unchanged into the save payload | If an alarm fires (and `onAlarmFired` updates `nextFireAt`) while the category edit screen happens to be open, a UI-held copy captured at screen-load time is stale by the time Save is pressed; writing it back would silently clobber the fresh value `onAlarmFired` already committed, and the validity check above would then reason about the wrong state entirely. Making the persistence layer authoritative for this one field removes the UI's need to track it at all and closes the race regardless of how long the screen was left open |
| Exact-alarm permission upgrade | A single device-wide `lastKnownExactAlarmAvailable` flag (DataStore); on a false→true transition (checked at the start of every `reconcileOnStartup()` pass), re-issue every enabled reminder's arm call using its existing `nextFireAt` via the exact API | A per-`Reminder` stored exactness flag; no upgrade path at all | Exact-alarm capability is a device-wide fact, not a per-category one, so a single flag suffices — no new column on `ReminderEntity` needed. Without any upgrade path, a reminder armed inexactly before permission was granted stays inexact forever unless the user happens to re-save it, contradicting the permission banner's implied self-healing (§ Category Edit Integration). `rearmAll()`'s boot/clock-change pass and every fresh `enableReminder` call already re-check permission live at arm time (Arming above), so only a reminder neither path touches — one sitting untouched with an already-valid `nextFireAt` — needs this separate path |
| Startup reconciliation staleness threshold | A buffer past `nextFireAt`, not "any amount in the past": 10 minutes if the device could schedule exact alarms *as of the start of this pass* (`wasExactAvailable` — the stored `lastKnownExactAlarmAvailable` flag, read before this pass's own upgrade-check or update), 30 minutes if not | Treat any past `nextFireAt` as stale immediately (original design); a per-category mutex or busy-signal shared with `onAlarmFired`/`rearmAll()`; a fresh live permission read at buffer-computation time | Delivering a reminder's alarm can itself cold-start the app process (if it wasn't already running) to invoke `ReminderReceiver` — and `Application.onCreate()`, which launches `reconcileOnStartup()`, always runs before Android then instantiates and calls the receiver. So a `reconcileOnStartup()` pass reacting to "any amount in the past" would very often race the very alarm fire it was woken up to help deliver, re-arming a reminder `onAlarmFired` is about to correctly reschedule anyway. A shared busy-signal can't fully close this race either, since `reconcileOnStartup()` could check it before the racing handler has even started (a fixed ordering guarantee, not a timing coincidence) — closing that gap needs an added grace delay anyway, which is no simpler than a buffer. The buffer must match the *actual* scheduling mode every currently-armed alarm was armed under, not a fresh live check, because a live check can read "exact" (tight 10-minute buffer) for a reminder that is, in fact, still armed inexactly and hasn't been walked to exact yet — wrongly declaring it stale before its legitimately looser delivery window has elapsed, exactly during the transition pass meant to walk it over. 10 minutes for the exact case matches `docs/high-level-design.md`'s documented ~9-minute worst-case Doze slip, rounded up for margin; 30 minutes for the inexact case has no equivalent documented platform figure and is a conservative placeholder |
| Exact-alarm upgrade and staleness recompute as one branching pass | A single loop over enabled reminders: null-or-stale `nextFireAt` recomputes and arms; only a non-null, not-stale one (sharing the same buffer) is eligible for the upgrade re-issue | Two separate loops — an unconditional upgrade walk over every enabled reminder, then a separate staleness walk (original design) | The original two-loop design double-armed a stale reminder within one `reconcileOnStartup()` pass: the upgrade loop would arm it once at its stale, possibly already-past `nextFireAt`, and the staleness loop would immediately arm it again at a freshly recomputed one. The end state was correct either way (`AlarmManager` replaces via matching `PendingIntent`), but a stale instant armed via the exact API can fire almost immediately (`setExactAndAllowWhileIdle` doesn't refuse past trigger times), risking a spurious fire in the brief window between the two calls. Since the two conditions (null-or-stale vs. non-null-and-fresh-during-an-upgrade) are mutually exclusive by construction, a single loop with a branch removes both the double iteration and the need to reason about the two loops' conditions never overlapping |
| Source of "at least one category has an enabled reminder" | An observable read of the reminder store, asked as its own question | Map each category-list emission to a one-shot read of every enabled reminder | The derived form answers the question only when the category list emits, and enabling a reminder without editing a category field re-emits an equal list that `StateFlow` conflation drops — so the banner stayed hidden until something unrelated changed a category. It also loaded every enabled reminder on every unrelated category write, when all the caller wants is whether one exists |
| Checking the reminders channel, not just app-level notifications | Read the `reminders` channel's own importance alongside `areNotificationsEnabled()`, and report a blocked channel as its own problem with its own settings destination | Rely on `areNotificationsEnabled()` alone; treat a blocked channel as the same problem as app-level | Long-pressing a notification and tapping "Turn off notifications" blocks the *channel* and leaves the app enabled — so the most common way a person mutes something was the one case none of these surfaces could see, and reminders stopped appearing with nothing anywhere saying why. The two need separate messages because they are fixed in different places: one in the app's notification settings, one on the channel's own screen |
| What the permission surfaces report | One problem at a time — the two that stop a reminder being shown before the one that only delays it — with the message and the settings destination both chosen from that one problem, shared by the inline prompt, the list banner, and the save dialog | Report every problem at once; keep a single message that covers any cause; let each surface decide for itself | The three surfaces decided separately and disagreed. Notifications off means the reminder is never shown at all, exact alarms off means it still arrives but possibly late — so the banner opening "Alarms & reminders" when both were off sent people to fix the smaller problem, and the one message it showed talked about timing, which is simply wrong when nothing will appear. Naming the worse problem first means fixing it and coming back surfaces the next one, instead of fixing something and finding the same warning still there |
| Permission-state recheck trigger | `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` broadcast for exact alarms; window focus for notifications | An `ON_RESUME` lifecycle observer for both; polling while the screen is open | Since Android 10 every visible activity in multi-window mode stays `RESUMED`, so granting a permission in a Settings pane beside the app fires no resume and a resume-triggered prompt sits stale indefinitely — the case the app's own split-screen users hit first. The broadcast fires regardless of focus and exists on exactly the API levels (31+) where the exact-alarm prompt can appear at all, so it needs no fallback path. Notifications have no equivalent broadcast, leaving window focus as the closest multi-window-aware trigger |
| Already-logged suppression window sizing | Relative to the reminder's own schedule: `min(10% of the gap since this reminder's previous scheduled fire time, 1 hour)`, FIXED mode only | A fixed constant duration (e.g. always 1 hour); count/threshold-based (skip if N events already logged today); windowed against the *next* scheduled time instead of the previous one | A flat constant is wrong at both ends of the schedule spread: too generous for reminders spaced close together (would suppress an unrelated earlier nudge's fire), too stingy for reminders spaced far apart. Scaling with the actual gap since the previous fire (not the next one, which doesn't exist yet at fire time) makes an 08:00/20:00 reminder ignore an 08:05 log when checking whether to suppress 20:00, while still suppressing on a 19:55 log — the property a fixed window can't give without per-reminder tuning. The 1-hour cap keeps a once-daily reminder's window (a 24-hour gap would otherwise give 2.4 hours) from silently swallowing an entire afternoon's independent logging. RANDOM mode is excluded — see § Scheduling Engine |
| Suppression window anchoring under delayed delivery | Window runs from `scheduledAt` minus the lookback through `firedAt`; the backward walk that sizes the lookback pivots on `scheduledAt` | Anchor both ends to `scheduledAt`; anchor both ends to `firedAt` | The two instants diverge whenever the alarm is late — milliseconds under an exact alarm, hours under the `setAndAllowWhileIdle` fallback in Doze — so a single "fire time" cannot serve both roles. Anchoring both ends to `scheduledAt` leaves a user who logged at 21:00 still nagged by a 20:00 reminder delivered at 22:30, which is the most irritating notification the feature can produce. Anchoring both to `firedAt` breaks the case the sizing rule exists for, since a 19:55 log would fall outside a window that starts at 21:30. Spanning `scheduledAt - lookback` to `firedAt` covers both. The walk pivots on `scheduledAt` for a separate reason: it qualifies candidates strictly before the pivot, and `scheduledAt` is itself a scheduled time, so pivoting on `firedAt` returns the occurrence being delivered and collapses the lookback to the delivery jitter |

## Open Questions & Future Decisions

1. **Notification action buttons** ("Log now" inline action, "Snooze") — deferred; tap-to-open covers v1.
2. **Overnight window support** — see Decisions; revisit if requested.
3. **Global pause** ("mute all reminders," e.g. for vacation) — no such control in v1; each reminder is toggled individually.
4. **Outstanding reminders surviving a reboot** — the timeline's list is read from the notification shade (§ Notifications), so a reboot empties it, matching what Android does to every app's notifications. Making it survive means keeping the app's own record, which turns one source of truth into two that can disagree. The hook that would make a mirror honest already exists: `setDeleteIntent` fires when the user dismisses a notification by swipe or "clear all" — and, usefully, not when the app cancels it or when auto-cancel fires — so a stored list could learn about a dismissal it did not perform. Not built; noted so the path is not re-derived.
5. **Multi-device / account sync** — v1 is entirely local, single-device, so a `Reminder`'s scheduling state is implicitly device-scoped. If accounts or server sync are added later, whether reminders are per-device or synced across a user's devices is an open design question in its own right (e.g. does a reminder fire on every device, or only one?), and `nextFireAt` specifically is awkward to sync as-is — it's this device's record of what it last told its own `AlarmManager`, not a portable domain fact (see § Data Model, § Scheduling Engine). No action needed now; flagged for whenever sync design starts.
