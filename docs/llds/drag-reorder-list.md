# Drag Reorder List

## Context and Design Philosophy

`CAT-UI-002` requires drag-to-reorder on the category list, and the list has two levels (`MetaCategory` / `SubCategory`, per the HLD's "Two-level category hierarchy" decision). A drag gesture on a two-level list has to do two jobs at once — reorder among siblings, and optionally change which group an item belongs to (nest a category into a `MetaCategory`, or promote a `SubCategory` back to top-level) — and a single drop point has to disambiguate which job the user means.

This is split into its own LLD, separate from `category-management.md`, because the interaction model (drag pickup, drop-zone geometry, visual feedback) is generic enough that it doesn't need to know anything about categories — it operates on a tree of generic `(id, …, children)` items and reports a structural move. `category-management.md` owns the adapter that maps `Category` ↔ this widget's generic item shape and persists the result. If a second hierarchical list ever needs reordering, this file's design is the one to reuse; if it doesn't, no harm done — it still cost nothing extra to keep the widget's core decoupled from `Category`.

**Scope note:** this is a design for a Compose composable that lives in this app (`ui/components/DragReorderList.kt`), not a separate Gradle module or published library. "Could become a library later" only informs today's decision to keep the core decoupled from `Category` — it does not add packaging, public API stability, or distribution work now.

## Interaction Model

**Live reflow.** As the dragged row crosses zones, the rest of the list animates in real time to open a gap exactly where the item would land if dropped right now (Compose's per-item placement animation — `Modifier.animateItem()` — so surrounding rows slide smoothly rather than snapping). This is the standard Android reordering pattern (Keep checklists, Spotify playlists, Google Tasks, Trello) and is what this design settled on. A static list with only a drop-zone indicator (no reflow) was considered and rejected: without the list visibly making room, it's harder to tell at a glance how many rows you're moving past or whether a nest will land where expected, and no-feedback-until-drop reads as unresponsive.

**Pickup: a dedicated drag handle, not long-press.** A row hosted in this widget may already carry its own long-press gesture for other purposes (in this app, the existing context menu — Delete / Add to group / Move to another group / Remove from group). Drag must not collide with that, so each row shows a small handle icon (`Icons.Filled.DragHandle`, trailing edge, ≥48dp touch target) as the affordance — but the drag *gesture* is **not** hosted on the per-row handle. Instead a single gesture interceptor sits on the `LazyColumn`'s own modifier — outer to the list's internal scroll, so it gets first look at every touch on the **Initial** pointer pass, before the scroll's **Main** pass. On touch-down it finds the row under the pointer's Y (`listState.layoutInfo.visibleItemsInfo`) and checks whether the down landed within *that row's handle-icon bounds* — both axes, since the interceptor spans the full list width, so a touch on row content at a handle's Y must not read as on the handle. Only a down on a handle icon claims the gesture — consumed on the Initial pass, so the scroll can't compete — and, once the touch clears the slop threshold, picks that row up (waiting for slop means a tap on a handle does nothing — and there is no long-press wait either). A down anywhere else is left entirely unconsumed, so it falls through to the *same node's* internal scroll on the Main pass and scrolls the list normally (see § Why a LazyColumn interceptor). The handle icons are therefore a pickup affordance only, not a blanket capture of any column.

**Why a LazyColumn interceptor rather than per-row `pointerInput`.** The obvious implementation — a `pointerInput` on each row's own handle — cannot survive auto-scroll (see § auto-scroll below / DRAG-UI-004, DRAG-UI-015). A `LazyColumn` disposes items scrolled outside its composed window; when the dragged row's handle scrolls off-screen during a sustained edge auto-scroll, that handle's composable is disposed and its gesture coroutine is cancelled by structured concurrency *mid-drag*, dropping the whole drag. Hosting the gesture on the `LazyColumn`'s **own modifier** fixes this at the root: that node *is* the list, never an item in it, so it is never disposed while rows scroll under it — the single gesture coroutine outlives any individual row, and auto-scroll can move the entire list past the dragged row's original position without interrupting the drag. (Confirmed on-device: the dragged row's slot was disposed during a sustained auto-scroll and the drag kept tracking — DRAG-UI-015.)

Because the interceptor's modifier wraps the `LazyColumn`'s internal scrollable, it is *outer* to the scroll and sees every touch on the **Initial** pass, ahead of the scroll's **Main** pass. That pass ordering — not a node drawn on top — is what arbitrates pickup versus scroll. A down on a handle is consumed on the Initial pass, so the scroll never starts; a down that misses every handle is left entirely unconsumed and reaches the *same node's* scroll on the Main pass, which scrolls and flings natively (DRAG-UI-016). Once a handle drag is claimed, every subsequent move is likewise consumed on the Initial pass, keeping the drag exclusive for its whole lifetime.

Two other disposal-surviving hosts were tried and rejected:

- **A persistent overlay strip** — a handle-width `Box` drawn over the trailing edge as a *sibling* of the `LazyColumn`, hosting one custom pointer node. It outlived disposal too, but being a sibling it was opaque to hit-testing of the list behind it, so a non-handle touch it declined never reached the list to scroll. Forcing the list back into the hit path (`sharePointerInputWithSiblings = true`) then let *every* touch through and regressed pickup (this is the bug on-device validation caught). Hosting on the `LazyColumn`'s own node removes the sibling entirely: host and scroll are one node, so there is nothing to share and nothing to leak. (An even earlier attempt hosted `detectDragGestures` on the outer `Box` wrapping the *whole* widget; rejected because that `Box` spans the scrollable content area, so its gesture fought the scroll for every pointer.)
- **`movableContentOf` relocating the whole dragged row** (gesture included) out of the lazy item to the floating overlay, so the row's later disposal has nothing live to cancel. A spike confirmed composition *state* survives the move across the `LazyColumn`'s `SubcomposeLayout` boundary (enter count stayed 1, dispose count 0), but on-device the in-flight **pointer stream did not follow the node** to its new call site — the drag froze at pickup and only resumed if the user re-touched the handle. State preservation is necessary but not sufficient; pointer routing is what broke. The interceptor sidesteps the whole question by never moving the gesture node at all.

The interceptor is the settled sole gesture host — its one non-obvious assumption (that consuming a handle-down on the Initial pass reliably preempts the `LazyColumn`'s internal scroll while a non-handle down still falls through and scrolls) is confirmed on-device, so the temporary `useOverlayStrip` A/B parameter and its debug app-bar toggle that once let the strip and this host be compared at runtime have been removed.

**Only one drag at a time; no concurrent gestures elsewhere.** Touchscreens are genuinely multi-touch — unlike a desktop mouse, where one cursor inherently serializes all pointer interaction, a second finger really can touch a different row while the first is still mid-drag. While a drag is active, the widget renders a transparent overlay across the rest of the list that consumes any new touch — the same click-catcher pattern already used for `TimestampField`'s fields — so a second finger can't open another row's long-press context menu or start a second drag. The dragged row's own gesture, already attached before the overlay appears, keeps receiving its events normally regardless. This also means a delete (or any other long-press-triggered action) can't be initiated mid-drag; the reverse direction needs no extra handling at all — a modal `Dialog` (e.g. the delete confirmation) already blocks all touches outside itself by default, so a new drag can't start while one is open.

**Collapse-on-pickup, in two independent tiers.** These are two different concerns with two different triggers, even though they always co-occur under Trackr's current invariant:

1. **D's own children always collapse whenever D has children**, full stop — dragging the whole group as a floating multi-row block would be unwieldy if it's taller than the screen, regardless of anything else. This is purely a rendering-size concern, gated only on D's current child count, not on `canBecomeChild`.
2. **Every *other* row's children collapse when `!D.canBecomeChild`** — because that's the condition (per Eligibility) under which no row with `canHaveChildren = false` is ever a valid target for this drag, so hiding all of them loses no functionality and clarifies the "only headers are interactive right now" rule. This tier is independent of tier 1, not layered on top of it: it's gated purely on `canBecomeChild`, not on whether D has children. Under Trackr's invariant the two happen to always fire together (children ⟹ ineligible), but in a future domain where eligibility isn't tied to child count, a childless-but-ineligible D would trigger tier 2 alone (nothing of D's own to collapse, but every other row still collapses), and a D with children but still eligible would trigger tier 1 alone (its own children collapse as an oversized-block concern, but other rows stay expanded since they might still be valid targets).

Both tiers expand back on drop or on drag cancel.

Implementation requirement: collapse **in place**, not by filtering the underlying data list. Each row stays present in the `LazyColumn`'s item list with its existing key and index throughout — the per-row composable animates its own height to zero (`AnimatedVisibility` / `animateContentSize`) rather than the row disappearing from `items()`. This matters because `LazyListState` anchors scroll position by the index and pixel-offset of the first visible item, not by total height above it — as long as indices don't shift, content collapsing above or outside the visible window doesn't move whatever's currently on screen. Filtering the data list instead would shift every later item's index and break that anchor, which is exactly the jump this is meant to avoid.

Collapsing can easily leave the list shorter than the viewport (e.g. scrolled deep into a long list of large groups, now collapsed to one row per group). A scroll-position correction is needed once collapse settles so the list isn't left implying content past its new (shorter) end. The exact mechanism (explicit `animateScrollToItem` clamp vs. relying on `LazyListState`'s own remeasure correction mid-animation) is not settled here — build the straightforward version first and refine once it's running on a device, per how every other animation/gesture detail in this doc got nailed down.

**While dragging:**
- The picked-up row is pulled out of normal list flow and renders as a floating element tracking the pointer in **both axes** (elevated shadow, slightly raised — see Visual Design) — it follows horizontal finger movement too, matching the feel of every other reference app, even though horizontal position carries no meaning here. Zone/target detection only ever reads the **vertical** position (which row, which band); horizontal offset is purely cosmetic. Everything else is ordinary list content.
- As the pointer crosses row boundaries, the current target row and zone (see Drop Zone Geometry) are recomputed; the widget recomputes the **hypothetical full order** that would result from dropping right now and feeds it back into the list, so the surrounding rows (including the open gap — at the dragged item's depth for before/after, indented one level for a nest) animate into that hypothetical arrangement live. A light haptic tick fires whenever the gap's position changes, so the user can feel the "snap" points without watching closely.
- Auto-scroll kicks in when the pointer is within ~64dp of the top/bottom of the visible list, scrolling at a constant rate until the pointer moves away from the edge. (Scaling that rate by how deep into the edge zone the pointer sits is a deferred refinement — see Open Questions § Deferred.) The drop position is re-evaluated on **every scroll step**, not only on pointer movement: the finger is typically held still at the edge while content scrolls beneath it, so treating each scroll as a drag event keeps the target (and the open gap) tracking the rows passing under the pointer rather than freezing where the pointer first reached the edge — otherwise the gap drifts arbitrarily far from the finger as the list scrolls, and a drop after a long scroll lands at a stale target. A pointer beyond the viewport's top or bottom edge resolves as though positioned *at* that edge, so a finger dragged off the end of the widget still targets the edge-most row.
- If the pointer is over a row that offers no valid zone for the item being dragged (see eligibility rules below), the gap simply stays at its last valid position — there is no "blocked" visual, the drop target just doesn't respond.

**On drop:** a confirm haptic fires and the widget reports a `DragMoveResult` (see Generic Widget API) to the caller, along with an `onSettled` callback. Because the list is already showing the live hypothetical position at the moment of release, there's no separate "settle" animation — the floating row drops into the gap that's already open, and the dropped row continues rendering at that position (no longer floating, just an ordinary row there) using the same hypothetical order the drag was already showing.

**Settling.** The caller's own `items` won't reflect the move yet — persisting it is the caller's job, and may not even be synchronous (a confirmation dialog, an async write). Until the caller calls `onSettled()`, the widget keeps rendering from the hypothetical order it already had (not from whatever `items` says, which is still the *pre-move* list) and blocks new drag pickups, the same way an active drag already blocks a second touch (see "Only one drag at a time" above) — so nothing can be dragged again before the gesture that just happened has actually finished, and the row can't flash back to its old position and then re-animate forward the instant `items` catches up. Once `onSettled()` is called, the widget drops its frozen copy and renders directly from `items` again: if the caller persisted the move, `items` already matches what's on screen, so there's no visible change; if the caller aborted instead (a cancelled confirmation dialog, a failed write), `items` is back to its pre-drag state, and the row animates back to where it actually started — the same `Modifier.animateItem()` machinery already driving every other reflow, not a special case.

## Drop Zone Geometry

These zones drive the live-reflow gap position described above — recomputing the zone on every pointer move is what feeds the "hypothetical order" the list animates toward. Each candidate target row is divided into vertical bands, and both the band count and what the bands mean depend on T's role — not just whether nesting is eligible at all.

**Per-row zone meaning** (T = the row under the pointer, D = the row being dragged), assuming D `canBecomeChild` (D is currently eligible, by caller-supplied domain policy, to become a child — see Eligibility below for the case where it isn't):

- **`!T.canHaveChildren`** (in this app, T is a `SubCategory` — always has a parent, can never receive children): **2 bands, 50/50.** Top = "insert before T" (sibling, T's own current parent group). Bottom = "insert after T" (sibling, same group). No middle band — `T.canHaveChildren` is false, so T is never a nest target regardless of anything else. (A contradictory `!canHaveChildren` row that nonetheless *has* children is a defined garbage-in case — see Generic Widget API § "one defined edge case" below; the row itself still behaves exactly as here, only the treatment of *its children's* bands differs, and that part is a spec-vs-implementation divergence left unfixed because the input is unreachable.)
- **`T.canHaveChildren` and T currently has no children** (in this app, T is a childless `MetaCategory`): **3 bands, 25/50/25.** Top = "insert before T" (joins T's own current sibling group). Middle = "nest into T" (T's only child — start and end are the same position when there are no existing children, so there's no ambiguity to resolve). Bottom = "insert after T" (joins T's own current sibling group).
- **`T.canHaveChildren` and T currently has children** (in this app, T is a `MetaCategory` with existing `SubCategory` children): **2 bands, 50/50.** Top = "insert before T" (joins T's own current sibling group, same meaning as above). Bottom = "nest into T, as its **first** child" (prepended — not appended). Appending at the *end* of an existing group is instead done directly on that group's last child's own "after" band, per the rule below — the header's own nest band always represents the position closest to the header, which is the front of the list, not the back.

"T currently has children" here is read **directly from the tree** — `T.children` (excluding D, which is conceptually lifted out for the duration of the drag, so a T whose only child is D reads as childless) — not from `canBecomeChild` and not a separate caller-supplied field. This is deliberately kept separate from `canBecomeChild` even though, in this app, "T has children" and "`!T.canBecomeChild`" always agree for a `MetaCategory` — that agreement is a fact about *this* domain's rules, not something the widget should rely on. `canBecomeChild` answers a domain-policy question the widget can never infer; "has children right now" is a structural fact the tree states outright. Collapsing them into one field would work today but would silently break the moment a future caller's eligibility rule didn't happen to coincide with child count.

The general rule underlying all "before/after" bands: **dropping before/after row T always means "join T's own current sibling group, at this position."** This single rule unifies plain reordering, reparenting, and promotion between groups with no special cases. In this app specifically: dropping before/after a `MetaCategory` always means "as a top-level item" (this *is* "remove from group," for free, when D currently has a parent), and dropping before/after a `SubCategory` always means "as a child of that `SubCategory`'s parent" (this *is* "move to another group" or "add to group," for free, landing at a specific position instead of always-appended). The only thing this rule can't express on its own is joining a group without referencing an existing child — that's what the header's own nest band (above) is for.

**Eligibility** (the rules below are generic; the *values* fed into them are domain policy — for this app, justified by the HLD's two-level invariant, "a category with children cannot be re-parented; a category with a parent cannot receive children," encoded in the adapter — see § Category-Management Integration and `docs/llds/category-management.md § Drag-to-Reorder: Adapter & Persistence`):

| Condition | Effect |
|---|---|
| `!D.canBecomeChild` (in this app: D is a `MetaCategory` with ≥1 `SubCategory`, so it's not currently eligible to become a child) | No nest band ever appears, on any row, regardless of T's type or child count — overrides all three per-row cases above. Every row with `canHaveChildren = true` instead offers a plain 50/50 before/after-joins-its-own-sibling-group split; every row with `canHaveChildren = false` offers **no zone at all** (would require D to join it as a child, which the invariant forbids while D has children). |
| T is D itself | No zone (can't drop a row on itself). |
| Otherwise (`D.canBecomeChild`) | The three per-row-type rules above apply as stated, including dropping a row back into its own current group (a no-op-shaped but harmless "reposition within the same group" outcome). |

**End-of-list drop:** the empty space below the last rendered row is treated as joining the top-level sibling group, appended at its end, regardless of the depth of the last visible row (in this app: regardless of whether it's a `SubCategory`) — dragging to the very bottom of the whole list reads as "last top-level item," not "buried inside whichever group happens to render last."

## Generic Widget API

The widget (`DragReorderList`) knows nothing about `Category`. It operates on an **ordered tree** of generic items — each node carries its own children, so the parent/child structure is stated outright rather than encoded as a depth integer plus an ordering convention:

```kotlin
data class DragListItem(
    val id: String,
    val canHaveChildren: Boolean,  // false for any item whose own row can never accept a nest-drop,
                                    // regardless of its current child count (domain policy)
    val canBecomeChild: Boolean,   // false if this item is not currently eligible to become a child
                                    // of anything (domain policy — for Trackr this happens to mean
                                    // "has no children of its own," but the widget doesn't assume that)
    val children: List<DragListItem> = emptyList(),  // nested items, in order; a leaf is emptyList()
)
```

There is **no `depth` field**: a node's depth is its position in the tree. The tree may nest to any depth — the widget imposes no limit (Trackr caps it at one level, but that cap is the *app's* concern, enforced by `Category.parentId` in the adapter, never by the widget). The tree representation makes malformed inputs unrepresentable: there is no way to express a child with no parent, or a level skipped (a depth-2 item directly under a depth-0 item with no depth-1 between), both of which a flat `(id, depth)` list could encode and the widget would then have to defend against.

**Preconditions and one defined edge case.** Ids must be unique across the *entire* tree, not merely within a sibling list — the widget keys rows and resolves moves by id. The caller supplies the tree already ordered (top-level `items` in order, each node's `children` in order) and does **not** pre-flatten it; the widget flattens it internally (see Internal representation below). One representable-but-contradictory input is defined for completeness rather than supported: a node N with `canHaveChildren = false` that nonetheless carries a non-empty `children` list (the adapter never produces this — it's garbage-in). N itself renders and behaves as an ordinary `canHaveChildren = false` row (before/after bands at its own level, never a nest band). N's children render too, but **no before/after band** ever appears on any of them — a sibling drop there would add to or reorder N's *own children group*, which N is declared unable to have. A **nest** band is still offered on a child C exactly when `C.canHaveChildren = true` (with C's normal nest geometry), because nesting into C concerns C's *own* group, independent of N's prohibition; a child with `canHaveChildren = false` therefore offers no band at all. The principle: N's contradiction only suppresses operations on N's children *group*, not operations on the children's own subtrees. Garbage in, but well-defined.

> **Known divergence (intentionally unfixed).** The implementation does *not* currently honor the "no before/after band on N's children" clause: the flattened drag math resolves a child's zone from the child's own `canHaveChildren`, never consulting N's, so N's children still offer their normal before/after bands. Enforcing the clause would require threading each row's parent `canHaveChildren` into zone resolution (`dropZone` / `computeDragTarget`). This is left unfixed deliberately because the input is unreachable: the only node type the category adapter gives `canHaveChildren = true` (and therefore the only node that ever receives children) is `MetaCategory`, so an N with `canHaveChildren = false` *and* children cannot occur. If a future caller can construct such a tree, this becomes a live bug to fix here.

`canHaveChildren` / `canBecomeChild` are supplied per-node by the caller — both are domain-policy questions the widget has no way to answer on its own. The widget doesn't need to encode "only top-level items can have children" as a rule of its own; that rule lives in the category-management adapter, where it's actually justified by the HLD invariant.

"Does node T currently have children" is used *only* to pick 3-band vs. 2-band nest layout on a nest-eligible target, never for eligibility itself. It is read straight off `T.children` and deliberately kept separate from `canBecomeChild` — see Drop Zone Geometry above for the source-and-separation rule and why.

**Internal representation.** A `LazyColumn` and the pointer-Y hit-test against `visibleItemsInfo` both need a flat, depth-annotated row list, so on input the widget flattens the tree depth-first (each node immediately followed by its children, in `children` order) into an internal `(item, depth)` list and runs all drag math — zone resolution, hypothetical reorder, sibling-group computation — over that. The tree is the public contract; the flat list is a private derivation. On drop the resulting flat order is mapped back into the result below: `newParentId` is the moved item's immediate enclosing node in the resulting order (the nearest preceding shallower item, or null at top level), and `orderedSiblingIds` is that destination group's run.

On drop, the widget reports:

```kotlin
data class DragMoveResult(
    val movedId: String,
    val newParentId: String?,           // id of the moved item's new immediate parent,
                                         // or null if the moved item is now top-level
    val orderedSiblingIds: List<String>, // full ordered ids of the destination sibling group, including movedId
)
```

```kotlin
@Composable
fun DragReorderList(
    items: List<DragListItem>,          // the top-level nodes, in order; each carries its own subtree
    onMove: (result: DragMoveResult, onSettled: () -> Unit) -> Unit,
    content: @Composable (DragListItem) -> Unit,  // renders one row; invoked for nested nodes as well as
                                                   // top-level, lazily — only as the LazyColumn composes
                                                   // each visible row, not eagerly for the whole tree
)
```

Internally, while a drag is active the widget tracks its own hypothetical reordering of the flattened `items` (recomputed on every zone change) purely to drive the live-reflow animation described above — `items` from the caller doesn't need to change mid-drag. `onMove` fires exactly once, on drop, with the final result and an `onSettled` callback (see "Settling" above) — the widget knows nothing about *why* settling might take a while (a confirmation dialog, an async write, nothing at all) or whether it ultimately succeeded; it only needs to know when it's over. `onSettled` must eventually be called exactly once per `onMove` call, whatever the caller decided — there's no way to express "I'm never going to decide," and a caller that drops the callback leaves the widget frozen indefinitely.

**Drag state holder.** All of the widget's mutable drag state lives in a single file-private `DragReorderState` class rather than as a dozen loose `remember { mutableStateOf(...) }` declarations at the top of the composable, constructed once per `DragReorderList` via a private `rememberDragReorderState()` factory (which threads a `rememberLazyListState()` into the holder so scroll position keeps its saver). The holder is a plain `remember`ed container (not `rememberSaveable` — an in-flight drag is not restored across process death), and it owns the state *transitions* too: pickup, per-move update, target/zone resolution, drop-and-maybe-move, and cancel are methods on the holder.

The state divides into two lifetimes. The **per-drag substate** — the picked-up row id and row size, the dragged row's live position, the current target/zone, and the pointer id driving the gesture — is grouped into a single nullable `ActiveDrag`: null when idle, non-null for exactly the drag's lifetime. Pickup constructs it; drop and cancel null it. This makes "is a drag active?" one nullable check and makes it structurally impossible to clear some per-drag fields and leave others stale — the flat-field predecessor cleared only four of its seven per-drag fields on reset, the other three staying dangling but harmless only because they were never read while idle. `ActiveDrag` is `@Stable`, carrying its set-once inputs (id, row size) as `val`s and its moving fields (`currentPosition`, target, pointer id) as its own inner `mutableStateOf`, so the `ActiveDrag` *reference* flips only at pickup/reset while per-frame mutations keep their fine-grained invalidation — collapsing the whole thing into one immutable value in one `mutableStateOf` would recompose every reader on every pointer move. `currentPosition` is the dragged row's top-left (seeded from its pickup offset, advanced by each move); `rowCenterY` — the row's vertical center that drop resolution and auto-scroll test against — is *derived* from it (`currentPosition.y + rowSize.height/2`) rather than stored, so it can't drift out of sync. The **cross-drag state** stays directly on `DragReorderState`: the frozen `settledDisplayOrder` (which deliberately outlives the drag — see § Settling), the last-rendered order, the live handle-bounds map, the root origin, and the `LazyListState`. Because those transitions depend on values that change every frame or every composition — the haptic and density handles, the caller's `onMove`, and the current flattened order — the holder captures none of them; each is passed in as a method argument at the call site. This keeps the holder a self-contained unit of drag state whose correctness doesn't depend on *which* composition's closure it was born in (the single pickup coroutine is launched once and never relaunched, so a captured-closure holder would silently bind to first-composition values). The holder is deliberately **not** part of the public API — there is no hoistable `state` parameter on `DragReorderList` today, because no caller needs to observe or share drag state; if one ever does, exposing the existing holder is a mechanical widening. See § Internal representation for the flat-order data the holder carries, and the Decisions table for why the holder is a class rather than scattered remembers.

## Category-Management Integration

The category list is the only current caller. How it maps `Category` ↔ the widget's `DragListItem` tree, gates a reparent on a value-type change, and persists a drop — the repository's `saveCategory` call, the destination-group `sortOrder` reindex, and its transactional reconciliation against live state — is category-management's concern, not the generic widget's. It is specced as `CAT-UI-080`/`CAT-UI-081`/`CAT-UI-082` and designed in `docs/llds/category-management.md § Drag-to-Reorder: Adapter & Persistence`. The widget's only obligations to any caller are the `DragMoveResult` contract (§ Generic Widget API) and the `onSettled` protocol (§ Settling).

## Visual Design

- **Drag handle**: `Icons.Filled.DragHandle`, trailing edge of each row, 48dp touch target (icon itself smaller, padded), vertically centered on the row (the row centers its children, so the handle sits mid-height rather than pinned to the top of a taller row). Hidden entirely when the list has only one row (no valid drop target exists, so no point offering the gesture). The gesture is hosted on the `LazyColumn` interceptor, not on the handle, so the handle is a pure affordance. While a row is being dragged its in-list handle stays mounted but is drawn invisible (`alpha = 0f`): it must remain in composition and layout so its `onGloballyPositioned` bounds stay current for pickup hit-testing, but it should not read as left behind with the static placeholder. A second, purely decorative copy renders in the floating row instead, so the handle reads as attached to the thing moving under the finger (matching every reference app).
- **Floating dragged row**: shadow elevation raised (e.g. `8.dp`), full opacity, same width/content as the row at rest, plus its own (non-interactive) drag handle icon trailing it — no scale change beyond the shadow, to keep label legibility while moving.
- **The gap itself** (before/after): a row-height **placeholder box** opens at the drop position, at the target's own depth (full-width for a depth-0-level gap, indented to match the existing indent of deeper rows — in this app, `SubCategory` rows — for a within-group gap) — surrounding rows animate to make room via `Modifier.animateItem()`. Within that depth-indented region, the placeholder is further inset by a small margin (4dp) and drawn as a rounded-corner (8dp) rectangle, filled `primaryContainer` with a `primary`-colored border, rather than a flush-edge solid block — the inset/border/rounding read as a deliberate "card" rather than a stray colored bar, the same visual grammar as the rest of Material3 surfaces in this app. It's a filled placeholder, not literal empty space: empty space would only be visible *while* rows are mid-animation sliding apart, and would be indistinguishable from plain background the instant things settle — a tinted box is readable in any single static frame, not just inferable from motion. This is the primary "where will it land" cue; no separate indicator line is needed since the placeholder's position and indentation already show it. The indent itself is driven by `animateDpAsState`, not a plain computed value — depth can change in the same hypothetical-order update that changes position (crossing into or out of a nest), and animating only the position (via `animateItem()`) while the indent snapped instantly read as the row sliding into place and then hopping sideways once it settled; animating both together so they complete in step fixes that.
- **No separate highlight on the target row for a nest.** A nest (middle band when childless, bottom band when already has children) is communicated by the placeholder's own depth alone — it renders one level deeper than the target, immediately adjacent to it — with no additional tint on the target row itself. (An earlier version of this design also tinted the target row, as a redundant cue meant to disambiguate the childless-target case, where the nest band and the after band both place a placeholder in the same spot directly below the target, differing only by indentation. Once the placeholder's indentation actually rendered correctly — initially a bug, not a design gap — and once equivalent target+zone pairs were canonicalized to stop reporting spurious changes (see Decisions), the extra highlight read as visual noise rather than a help and was dropped in favor of indentation alone.)
- **No change** for a row offering no valid zone for the current drag (see Eligibility table) — the floating row simply passes over it inert; the gap stays wherever it last validly was.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| Drag style | Live reflow (list animates open a gap at the drop position as you drag) | Static list + drop indicator only on the target row ("blind drag") | Standard pattern for this kind of list on Android (Keep, Spotify, Google Tasks, Trello); a static list with only an indicator gives less feedback about exactly where a drop will land and reads as unresponsive |
| Pickup gesture | Dedicated drag handle icon; the drag begins on the icon once the touch clears touch slop (a tap on the handle is inert) | Long-press anywhere on the row | Long-press is already the context-menu gesture on this row; reusing it for drag would collide |
| Gesture host | Gesture interceptor on the `LazyColumn`'s **own** modifier — outer to the internal scroll, so it hit-tests every touch-down on the Initial pass and consumes only a down that lands on a handle icon (pointer-XY hit-tested to a row), leaving everything else for the scroll | Per-row `pointerInput` on each handle; a persistent overlay strip (handle-width sibling `Box` drawn over the handle column); `movableContentOf` relocating the dragged row out of the lazy item to the floating overlay; `detectDragGestures` on the outer `Box` wrapping the whole widget | Per-row hosting is killed when the `LazyColumn` disposes the dragged row's handle as it auto-scrolls off-screen — structured concurrency cancels the gesture coroutine mid-drag (DRAG-UI-004 / DRAG-UI-015). Hosting on the list's own node survives that (the node *is* the list, never an item) **and** arbitrates pickup-vs-scroll by pass order alone: the interceptor is outer, so it consumes a handle-down on the Initial pass before the scroll's Main pass, and leaves a non-handle down for that same node's scroll. The overlay strip also survived disposal but, being a sibling, was opaque to the list behind it — sharing the pointer back (`sharePointerInputWithSiblings`) to fix scrolling then let *every* touch through and regressed pickup. `movableContentOf` survived disposal in principle but the in-flight pointer stream did not follow the relocated node — the drag froze at pickup (on-device). The outer-`Box` variant fought the scroll for every pointer. The interceptor needs neither a sibling nor a relocation: host and scroll are one node |
| Non-handle touch | Left entirely unconsumed on the Initial pass, so it reaches the *same node's* internal scroll on the Main pass and scrolls/flings natively (DRAG-UI-016) | Overlay strip sharing the pointer with siblings (`sharePointerInputWithSiblings = true`); strip driving `listState.scroll` itself for non-handle drags | With the gesture host on the `LazyColumn`'s own modifier there is no sibling to be opaque and nothing to share — an unconsumed down simply falls through the same node to its own scroll. The strip approaches (share, or re-drive scroll) were only needed because the strip was a separate node drawn *in front of* the list; removing the separate node removes the problem they solved |
| Zone split | 25/50/25 only for a childless `canHaveChildren = true` target; 50/50 for a `canHaveChildren = false` target or a `canHaveChildren = true` target that already has children | Even thirds (33/33/33) always; uniform 25/50/25-or-50/50 keyed only on "is nest eligible at all" (not on T's own child count) | A wide middle band makes "nest" a confident target when it's the only way to populate a still-empty group; once a group has children, picking a position via the children's own before/after bands is more precise than a single coarse nest band, so the header narrows to "before the whole group" vs. "first child," and appending at the end happens at the last child's own row instead |
| Unifying before/after with reparent/promote | One rule ("before/after T always joins T's own group") covers reorder, reparent, and promote-to-top-level | Separate explicit gestures/menus per operation | A single positional rule removes special-casing in both the widget and the adapter; in this app, the existing context-menu actions (Add to group, Move to another group, Remove from group) become drop-position special cases of the same persistence call rather than separate code paths — though those context-menu actions themselves are not being removed (see Open Questions) |
| Widget input shape | Recursive tree: `DragListItem(id, canHaveChildren, canBecomeChild, children)`; depth derived from nesting; flattened internally for rendering/hit-testing | Flat pre-ordered `List<DragListItem>` with an explicit `depth: Int` + positional sibling-group inference; widget takes `Category` directly | The tree states parent/child structure outright instead of encoding it as a depth int plus an ordering convention the widget must reconstruct — malformed inputs (a depth-2 row under a depth-0 row, a child with no parent) become unrepresentable, and the result speaks `newParentId`/`orderedSiblingIds` directly instead of the generic "group anchor" vocabulary the flat form forced. Arbitrary depth falls out of the recursion for free (not speculative work); the two-level cap stays the app's concern, enforced by `Category.parentId` in the adapter, never by the widget. Internally the widget still flattens to a depth-annotated list, so the existing drag math is retained — the change is concentrated at the input parse and the result mapping. Taking `Category` directly is still rejected: it would couple the widget to the domain for no gain |
| "T has children" read from the tree, not a field | Read `T.children` directly (excluding D when D is one of them) | A third caller-supplied `hasChildren` field, or collapsing it into `canBecomeChild` | With a tree input the child relationship is explicit, so the band-count question (childless ⇒ 3-band, has-children ⇒ 2-band) is answered by reading `T.children` directly — no positional inference, no extra field, and no false coupling to `canBecomeChild`; full rationale in Drop Zone Geometry |
| Collapse scope for a children-bearing drag | Two independent tiers, each with its own trigger: D's own children collapse whenever `D.hasChildren`; *every other* row's children collapse whenever `!D.canBecomeChild` (not conditioned on tier 1 at all) | A single trigger collapsing everything whenever `D.hasChildren` | The two concerns have different justifications (D's own size vs. other rows' guaranteed inertness) that only coincide because Trackr's `canBecomeChild` happens to be tied to child count — collapsing everything off a single `hasChildren` trigger would over-collapse rows that might still be valid targets under a different (future) eligibility rule, and would under-collapse a hypothetical childless-but-ineligible D. Splitting the trigger costs nothing now (the two tiers always fire together here) and keeps the widget honest about which concern justifies which collapse |
| Collapse implementation | Collapse in place — animate each row's own height to zero, all rows stay present in the `LazyColumn` item list at their existing key/index | Filter the underlying data list down to `canHaveChildren = true` rows only while collapsed (in this app, `MetaCategory`s only) | `LazyListState` anchors scroll by (index, offset) of the first visible item; keeping indices stable means content collapsing above/outside the viewport can't move whatever's currently on screen. Filtering the data list would shift every later item's index and break that anchor — the exact jump this choice avoids |
| Equivalent target+zone pairs | Canonicalize before comparing: "after row T" and "before T's next sibling" (and likewise "nest as T's first child" vs. "before T's current first child") resolve to the same `computeMoveResult` output, so crossing that boundary is treated as no change at all — no haptic, no target/zone write | Compare raw `(targetId, zone)` pairs directly | Two different target+zone inputs can describe the identical drop position (same `DragMoveResult`) by construction of the unifying before/after rule. Comparing the raw pair instead of the resulting position meant the pointer crossing that exact boundary fired a spurious haptic and briefly re-resolved state for a move that didn't actually change anything — read as jumpiness on a real device even though each individual resolution was internally consistent |
| Drag state container | A single file-private `DragReorderState` class (constructed via a private `rememberDragReorderState()` factory) holding the cross-drag state plus the `LazyListState`, with the per-drag substate grouped into a nullable `ActiveDrag`, and owning the state transitions as methods that take their volatile inputs (haptics, density, `onMove`, current flattened order) as arguments | A dozen loose `remember { mutableStateOf(...) }` at the top of the composable (the prior shape); a flat field list on the holder with a `reset()` that nulls each per-drag field by hand; a public hoistable `state: DragReorderState = rememberDragReorderState()` parameter mirroring `rememberLazyListState` | Collecting the state into one holder makes the transitions testable/auditable as a unit and gives the deferred node-graph refactor (Open Questions § Deferred item 3) a single place to change `settledDisplayOrder`'s element type. Grouping the per-drag fields into a nullable `ActiveDrag` (null == idle) ties their lifetime together — pickup and reset become one assignment each, and no reset can clear some fields and forget others (the flat shape cleared four of seven). `ActiveDrag` stays `@Stable` with its high-frequency fields as inner `mutableStateOf` so the reference flips only at pickup/reset and per-frame mutations keep fine-grained invalidation, rather than recomposing every reader on each move. Passing volatile inputs per-call rather than capturing them keeps the holder correct regardless of which composition's closure created it — the pickup coroutine is launched once and never relaunched. The holder stays **private**, not a public hoistable parameter: no caller needs to observe or share drag state, so exposing it now is unused public surface (YAGNI); widening it later is mechanical if a caller ever needs hoisting |
| Scroll stability during reflow (DRAG-UI-020) | On every target change during a drag, capture the pre-reflow `(firstVisibleItemIndex, firstVisibleItemScrollOffset)` and re-assert it after the reflow via `requestScrollToItem`, overriding `LazyColumn`'s key-based scroll preservation just for that measure | Let `LazyColumn` preserve scroll by key (the default — the bug); guard the pin to only the cases where the top-slot occupant changes (needless — see rationale); pin the first visible **non-dragged** row (fails: that row itself shifts when the placeholder crosses it); pin a measured pixel offset of a non-crossed reference row (needless bookkeeping); don't reorder the `LazyColumn` at all — keep the dragged row's key at a fixed index and show the gap by translation (kills the bug class by construction but reworks how DRAG-UI-002/003 render) | Keyed lazy lists preserve scroll by pinning the first-visible **key**; when that key is the dragged placeholder, the reflow relocates it and `LazyColumn` scrolls to follow — and each jump re-resolves the target against the new geometry and reflows again, cascading the list to the far end. The mirror image is just as wrong: when the reflow *prepends* the placeholder into the first slot (dragging a row up to become the first item), `LazyColumn` keeps the old first row pinned and tucks the placeholder above the viewport, hiding the preview. Keys can't be dropped (the reflow animation, `Modifier.animateItem()`, needs them), so the fix counteracts the follow: re-assert the *numeric* scroll position after the reflow. This needs **no guard and no pixel refinement**: the target is always a visible row (an off-edge pointer clamps to the edge-most visible row, DRAG-UI-019), so the placeholder never lands above the viewport — which makes re-asserting `(index, offset)` universally correct. It's a no-op whenever the top slot's occupant is unchanged (it matches what `LazyColumn` would do anyway), and it's the fix when the dragged row leaves the top slot or its placeholder arrives in it — re-asserting the slot's index+offset preserves the **top** of that slot regardless of which row, or what height, now fills it (offset is measured from the item's top), and a reorder preserves total height, so everything below stays put too |
| Settling after drop | `onMove` carries an `onSettled` callback; the widget freezes (keeps showing the dropped hypothetical order, blocks new pickups) until the caller calls it | Detect settlement by comparing `items` against the dropped order on every recomposition (no callback); fall back to `items` after a fixed timeout | A comparison-based heuristic has no way to distinguish "the caller hasn't persisted yet" from "the caller persisted something that legitimately doesn't match" (e.g. a value-type-change conversion altering more than just position), and a timeout is either too short for slower persistence (real bounce-back, since `items` reverts to the stale pre-move list the instant the drag's own hypothetical order ends) or too long for a fast one (entire list frozen for no reason). A caller-signaled callback needs no inference and handles a cancelled write for free: the caller calls `onSettled` without having changed `items`, and the row animates back to where it actually started — the same reflow animation as any other move, not a special case |

## Open Questions & Future Decisions

### Resolved

1. ✅ **Context-menu reparent actions are kept**, for accessibility — "Add to group" / "Move to another group" / "Remove from group" remain the only reparent path available to anyone who can't perform a drag gesture; drag is additive, not a replacement.
2. ✅ **Move Up / Move Down actions should be added** to the long-press context menu, as the accessible (non-drag) path for pure within-group reordering — the kept context-menu actions (item 1) cover reparenting but not reordering, so reordering would otherwise have no non-drag path at all. This is a `CategoryListScreen` context-menu feature, not part of this widget — tracked as a deferred follow-up task in `category-management.md` (Open Questions § Deferred), not in this LLD's own implementation scope.
3. ✅ **Nest-via-header insertion position resolved by splitting on T's child count** — see the revised Drop Zone Geometry above: a childless nest-eligible target's nest band has only one possible child position; one with existing children (in this app, a `MetaCategory`) offers a 2-band split where the bottom band means "first child" (prepend), with appending at the end handled separately via the last existing child's own "after" band.
4. ✅ **Single-row lists hide the drag handle entirely**, rather than handling "no valid drop target exists anywhere" as a gesture-time edge case. When the list has only one row total, there is no other row to be before, after, or nested into, so the affordance simply isn't offered — `CategoryListScreen` renders no `DragHandle` icon for a row when `items.size == 1`.
5. ✅ **A children-bearing drag collapses children on pickup, in place, in two tiers** — D's own children always; every other row's children only when `!D.canBecomeChild` (see Interaction Model § Collapse-on-pickup and the Decisions table rows above). The exact scroll-position-correction mechanism for when collapse leaves the list shorter than the viewport is intentionally left unspecified — build the straightforward version, test on a real device, and refine, the same way the timestamp field's click-target and cascade behavior were settled by hands-on testing rather than predicted up front. That deferred correction is carried as its own spec, `DRAG-UI-017` (marked `[D]`), so the collapse behavior itself (`DRAG-UI-011`/`DRAG-UI-012`) reads as complete without absorbing an unbuilt clause.
6. ✅ **Gesture host settled: an interceptor on the `LazyColumn`'s own modifier**, using Initial-pass selective consumption to arbitrate pickup vs. scroll (see Interaction Model § Why a LazyColumn interceptor and the Decisions table). Three earlier hosts were tried and rejected — a naive per-row `pointerInput` (dies when the dragged row is disposed mid-auto-scroll), a persistent overlay strip (a sibling node, so sharing the pointer back to the list to let non-handle touches scroll regressed pickup), and `movableContentOf` relocating the dragged row (composition state followed the move but the in-flight pointer stream did not — the drag froze at pickup, confirmed on-device). The interceptor was confirmed on-device: handle pickup, non-handle scroll/fling (DRAG-UI-016), and an in-flight drag surviving the dragged row's disposal during sustained auto-scroll (DRAG-UI-015).

### Deferred

1. **Generalize eligibility to a caller-supplied pairwise predicate.** Today `canHaveChildren`/`canBecomeChild` are per-item booleans — sufficient because eligibility in this app only depends on each item's own state (whether it currently has children), not on which specific parent it's being dropped onto. If the widget is ever reused somewhere that needs pairwise rules (e.g. "this type can only nest under that type"), replace both booleans with a single caller-supplied predicate, something like `canBecomeChildOf(childId: String, parentId: String): Boolean` (argument order chosen to read as the question being asked — the original phrasing, `canBeChild(parentId, childId)`, is ambiguous about which id is which). This is strictly more expressive than the current booleans (they're recoverable as a predicate that ignores one argument) and collapses `DragListItem` down to just `(id, children)`. One thing this should *not* become the caller's responsibility for: structural validity (T is not D, and — relevant only once the tree nests beyond one level — T is not currently a descendant of D) is true for any tree regardless of domain, so the widget should keep enforcing that itself unconditionally rather than expecting every predicate implementation to get cycle-prevention right.
2. **No local drop target for an intermediate depth at the end of a deeply-nested group, beyond depth 1.** The "End-of-list drop" rule (above) special-cases only the very bottom of the *entire* list, mapping it to depth 0. It doesn't generalize: if the widget were ever reused for a tree deeper than two levels, dropping near the last row of a sub-group whose depth is more than one level below the group you want to join (e.g. the flattened order drops from depth 2 straight to depth 0, skipping over depth 1) has no local gesture for **appending** as a child of that depth-1 group. Its own nest band doesn't rescue this: a group that already has children exposes only a *prepend* band (bottom band = "first child," per Drop Zone Geometry — the header's nest band always represents the front of the group, never the back), so scrolling back up to it lands the row *first*, not last. The only way to land last is the indirect two-drag path: drop *before* the group's current final child — which joins that child's sibling group at that position, leaving the newcomer second-to-last — then drag the former final child up one slot so it sits ahead of the newcomer. **Deferred indefinitely** — Trackr's tree is capped at depth 1 by the HLD invariant, so this situation cannot occur here; it only becomes relevant if a future reuse of this widget needs depth ≥ 2.
3. **Store internal state as a node graph, not a flat depth-list — deferred refactor.** Today the widget flattens `items` into an `(id, depth)` list (`flatten`) and then re-derives every structural relationship from it by scanning depths: `siblingGroup`, `groupAnchorOf` (parent lookup), `childrenOf`, `hasChildrenStructurally`, and `countDescendants` are all "unflatten the tree back out of the flat list" helpers, and together they are the bulk of the widget's top-half helper code. An alternative representation keeps a **node graph** — nodes carrying `parent`/`children` references and the policy flags, with depth derived from the parent chain rather than stored — as the settled tree shape, plus a **display order** that is a flat `List<Node>` of *references into that same graph*, in depth-first render order. Structure queries then become O(1) property reads (`node.parent`, `node.children`) and those five helpers disappear; only the *order* stays flat, because rendering to `LazyColumn` and pointer-Y hit-testing against `visibleItemsInfo` are inherently positional. `dropZone` (pure band math) is unaffected; `computeMoveResult` keeps its `DragMoveResult` contract but reads structure off the nodes; `hypotheticalOrder` shrinks — the manual `depth = depth + delta` re-depthing goes away once depth is derived — but does not vanish, since it still splices the dragged subtree into a new flat reference projection.

   Two sharp edges make this more than a mechanical change, and are why it's deferred rather than folded into the state-holder work:
   - **Node identity becomes referential.** A node holding both `parent` and `children` cannot carry a structural `equals`/`hashCode` (the cycle would recurse), so nodes are reference-identity objects and any list-equality on the display order is identity-based — every current reliance on structural `FlatNode` equality must be audited before the switch.
   - **Stale instances across a settle.** Rebuilding the graph whenever `items` changes mints fresh node instances, so a `settledDisplayOrder` captured at drop holds the *previous* graph's nodes while the current graph holds new ones. Rendering tolerates this (rows key by `id`), but the invariant must be made explicit: while an order is frozen for settling — or hypothetically reordered mid-drag — render from that order, but resolve structure only against the current graph, never against stale captured nodes.

   This is expected to land *after* the state-holder refactor and will require a small, known follow-up there: `settledDisplayOrder` changes type from `List<FlatNode>` to `List<Node>` (references), so the holder field and the methods that set it move with it. Accepted as cheap rework rather than a reason to sequence the tree change first.

4. **Proportional auto-scroll speed.** DRAG-UI-004 auto-scrolls at a single constant rate whenever the pointer is inside the edge zone. A refinement scales that rate by how deep into the zone the pointer sits — near-zero at the zone's inner boundary, fastest at the very edge — so the user meters scroll speed by finger position, matching the feel of mature reorder lists. The edge-zone geometry and half-viewport clamp already computed for DRAG-UI-004 yield the depth fraction directly; the constant step just becomes `fraction * maxStep`. **Deferred:** the curve (linear vs. eased) and the max rate want on-device tuning, and the constant-rate version is a fine baseline — carried as its own spec, `DRAG-UI-018` (marked `[D]`), so DRAG-UI-004 reads as complete without absorbing an unbuilt clause.

   **The scroll-rate clamp is not DRAG-UI-019's clamp — don't reuse the clamped pointer.** DRAG-UI-019 clamps the pointer *position* to `[0, viewportHeight]` so an off-the-edge pointer still resolves a drop target and renders the placeholder against the edge-most row. The proportional rate instead clamps a depth *fraction* to `[0, 1]` measured over the edge band. They answer different questions (where the row lands vs. how fast to scroll) over different domains (the whole viewport vs. the 64dp edge zone), so the rate must derive its fraction from the raw pointer-Y, not the DRAG-UI-019-clamped value. The two happen to coincide at the very edge today (both saturate there), which is exactly why conflating them is an easy latent mistake to make.

5. **Move the DRAG-UI-019 edge clamp up to the UI layer.** The off-edge clamp (`y.coerceIn(0f, viewportHeight)`) currently lives inside `resolveHitDropCandidate`, the innermost pure hit-test — which therefore has to take `viewportHeight` only to clamp with it. The clamp is really a UI-position policy (pin the effective drag position to the visible viewport), not part of "which row/zone does this viewport-relative y hit," so it belongs at the `updateDropTarget` boundary where the position is produced; `computeDragTarget` and `resolveHitDropCandidate` would then take an already-clamped `y` and drop `viewportHeight` entirely, leaving a pure in-viewport hit-test. **Deferred:** DRAG-UI-019 is currently covered by cheap unit tests that drive `computeDragTarget` with out-of-range `y` (−50, 5000); moving the clamp up strands that behavior behind a laid-out `LazyListState`. Hold until end-to-end androidTest coverage exists for the off-edge behavior, then move the clamp all the way up.
